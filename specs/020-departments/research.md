# Research：部门与分派范围（020）

## R-01 为什么物化路径，而不是递归 CTE 或邻接表遍历

子树查询（「我部门及所有下级」）是分派判定的热路径，每次拖拽都要算一次。

| 方案 | 读 | 写 |
|---|---|---|
| 邻接表 + 递归 CTE | 每次查询递归，深度大时慢 | 简单 |
| 物化路径 `path` | `WHERE path LIKE '/x/%'`，一次索引前缀扫描 | 移动部门要重写子树 path |
| 闭包表 | 最快 | 每次增删要维护 O(n²) 行 |

组织重组是低频事件（一年几次），分派是高频事件（每天几十次）。用写的复杂度换读的
简单，方向正确。**并且我们干脆不支持「移动部门」**——真要挪就建新部门 + 挪人，
比静默搬子树安全（搬子树要重写所有后代 path、还要考虑并发）。

## R-02 为什么是「每层一个范围」，而不是分派权限矩阵

矩阵（部门 A 可派给 B、C，不可派给 D）的问题不在存储，在**用户理解成本**：
谁配的、为什么我被挡住、改哪一条能放开——每次都要读一遍配置。

真实诉求只有一句「别让隔壁部门把活派过来」，三档范围（全公司 / 本部门及下级 /
仅本部门）就够。等真出现「研发能派给测试但不能派给销售」这种，再考虑向上建
「部门组」——那也比逐格授权简单。

## R-03 为什么默认不收紧（`all` 且未归属 = 不限）

如果升级后默认 `subtree`，所有没配部门的用户会立刻**只能派给自己**——一个安静的
生产事故：功能没坏，但所有人都说「拖不动了」。

所以：默认 `all`，未归属视为不限。代价是「刚建了部门但没把人归档时，限制不生效」，
这一点必须在 UI 上明说（我在组织页加了那句提示），否则管理员会以为自己配好了。

## R-04 为什么受限用户看不到范围外的人（而不是让他们选了再 403）

两种交互都「安全」，但成本不同：
- 下拉里全公司、提交时 403 → 用户白填一次，且不知道为什么有人不能选；
- 下拉里只有范围内的人 → 一开始就走不到错路。

实现上是 `list_options(db, actor_id)` 多一个过滤，一次索引查询。唯一要小心的是
**自己必须在列表里**（否则派给自己的路径断了）。

## R-05 为什么「派给自己」永远放行

取消分派/退回自己的活是一个真实动作。如果按范围拦，「受限部门的人连自己的活
都派不出去」——这没有业务意义，只有投诉。

代码里是一行早退（`if actor_id == target_user_id: return True`），但它挡住了
一整类「设计得很严但没法用」的问题。

## R-06 为什么删部门要显式把成员 `department_id` 置空

DB 层已经是 `ON DELETE SET NULL`，代码里再显式做一次，是为了：
1. 审计/测试能断言「人还在、只是没部门」；
2. 如果哪天有人把外键策略改成 CASCADE，代码层仍然保证不删人。

「删组织不该删人」是这类系统最容易出人命的地方，两条防线不算多。

## R-07 为什么先查重名再 INSERT

第一版实现是「插入 → flush → 查重名」，集成测试直接打回：`flush()` 那一刻
UNIQUE 约束就校验了，抛的是 `IntegrityError`（端点转 500），用户看到的是
「服务器错误」而不是「同一个上级下已有同名部门」。

改成「先查再插」，DB 的 UNIQUE 仍保留作为并发兜底。这类「先写后查」的错误在
有唯一约束的表上很常见，值得记一笔。

## R-08 为什么不做部门级可见性隔离

需求可见性现在是「创建者 ∪ 接收人 ∪ 项目参与者」（007/010）。加「部门内可见」
会立刻产生新问题：跨部门项目怎么办？依赖边跨部门怎么办？——而诉求里并没有
「不让别人看到」（那是项目共享的职责）。分派范围解决的是**谁能把活给谁**，
不是**谁能看到什么**。两件事分开做，各自都简单。
