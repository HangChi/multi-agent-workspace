# Feature 006 Research: 运行自动重试

> **Branch**: `feat/006-run-retry` | **Date**: 2026-11-18 | **Spec**: [spec.md](spec.md)

本文件记录 006 的关键决策与「为什么更简单的做法不行」。每条都能从代码验证。

---

## R-01 为什么不用 Celery 自带的 `self.retry()`

**候选方案**：在 `execute_run` 里 `raise self.retry(countdown=...)`，让 Celery 管重试。

**否定的理由**（三条，任一条都足够）：

1. **它会破坏「任务永远正常返回」的现有契约。** 今天 `execute_run` 的所有异常都被
   catch 后标 failed 并 `return "failed"`，Celery 认为任务成功完成。一旦改用
   `self.retry()`，异常会重新抛出、任务进入 Celery 的重试状态，而
   `task_acks_late=True` 会让这条消息在重试窗口内**重新投递**——
   同一时刻可能出现「Celery 的延迟重投」与「我们自己调度的重试」两个执行体，
   正是 spec FR-010 要防的重复执行。
2. **重试期间 Run 的状态无处安放。** `self.retry()` 之后 Run 在 DB 里是什么状态？
   我们没有机制把它标成「等待重试」，reaper 会在 30 分钟后把它当僵尸回收成
   failed（spec FR-012 直接违背）。
3. **退避策略不可配置。** countdown 是固定的，做不了 full jitter（spec FR-007）。

**采用**：保持「任务正常返回」，失败时若可重试，则由任务内部用
`apply_async(countdown=jitter)` 投递一个**全新的任务**，靠 Redis 锁保证同一时刻
只有一个执行体。这把「重试」变成一次普通的再次分配，语义与手动重试一致。

## R-02 为什么 full jitter 而不是固定退避

**候选方案**：固定 2s → 4s，不加随机。

**否定的理由**：多个 Run 往往因为同一个原因同时失败（网关重启、网络抖动）。
固定间隔会让它们在同一个秒数一起重试，把刚恢复的网关再次打挂——
这叫惊群（thundering herd），是重试机制最常见的自伤方式。

**采用**：AWS《Exponential Backoff and Jitter》的 full jitter 方案：
`wait = random(0, min(cap, base × 2^attempt))`。随机区间取满而不是取一半，
因为在最坏情况下（全部取到上限）它的分布仍然是最优的。

## R-03 为什么新增 `retrying` 状态而不是复用 `failed` + 角标

**候选方案**：状态仍是 `failed`，只加 `next_retry_at` 字段，前端显示角标。

**否定的理由**：

1. **看板与筛选会说谎。** `failed` 是终态语义。用户按「失败」筛选，看到一个
   其实 4 秒后就会自己成功的任务，会去手动重试——而手动重试与自动重试会撞锁，
   白费一次用户操作。
2. **状态机无法表达「这个终态其实还会动」。** 既有规则里 `failed → queued` 是
   重试的唯一出口；若 `failed` 同时表示「等待自动重试」，这条规则就歧义了。
3. **reaper 的判定要打补丁。** reaper 按 `status = failed AND updated_at < now-30min`
   捞僵尸；复用 `failed` 就得额外排除「有 next_retry_at 的」，这是一个容易漏的
   WHERE 条件，而漏掉的后果是重试被误杀。

**采用**：新增 `retrying` 中间态。代价是动状态机与 run_status 枚举，
但收益是每个既有机制（筛选、reaper、看板分列）都不需要打补丁——
新状态天然不在它们的处理范围内。

## R-04 为什么成本跨重试累计，而不是每次尝试重置

**候选方案**：每次尝试重置 `cost_cents`（今天手动重试的行为）。

**否定的理由**：

1. **数字对不上真实支出。** 重试花的 token 是真实发生的。重置后，看板上的月度
   成本会系统性低于网关账单，配额熔断也会偏松——用户以为还有额度，其实已超支。
2. **熔断会被绕过。** 既有熔断判据是 `run.cost_micros > cost_limit × 1M`。
   若每次尝试重置，一个上限 500 分的任务可以重试 3 次各花 490 分，
   实际支出 1470 分而从不触发熔断（spec FR-014 直接违背）。
3. **累计不需要额外机制。** `runner` 里已经是 `run_cost_micros += step_micros`
   的增量累加，只要重试时**不重置这个字段**，累计语义自然成立。

**采用**：重试（自动与手动）都不重置成本。手动重试端点原先重置 `cost_cents/error/
current_step` 的行为改为只重置 `error/current_step`，成本保留——这是 001 行为的
一处刻意变更，spec FR-020 保证的是**外部契约不变**（路径/状态码/响应体），
而响应体里的成本数字本来就该是真实的。

## R-05 为什么「无法归类的未知异常按业务类处理」

**候选方案**：未知异常也重试（宁可多重试一次）。

**否定的理由**：未知异常里最可能的是代码 bug（`AttributeError`、
`TransitionError`）。对 bug 重试 3 次意味着同样的栈错误 3 次、3 倍的日志噪声、
以及 3 倍可能已产生的部分成本。而瞬时故障的特征是明确的（连接失败、超时、5xx），
白名单可以列全。

**采用**：瞬时类用白名单显式列举，其余一律业务类。重试保守原则：
**只对确知会自愈的失败重试。**

## R-06 为什么不给 pipeline 父 Run 自动重试

**候选方案**：父 Run 失败也自动重试，把整条链路再跑一遍。

**否定的理由**：

1. **成本是 N 倍。** pipeline 有 N 个阶段，重跑一次父 Run = N 次执行。
   瞬时故障只影响其中一个阶段，重跑全链是最贵的修法。
2. **中间产物已入库。** 前几个阶段的 result 已写入 DB 与制品存储，重跑会产生
   重复制品，而现有收敛逻辑不处理「部分阶段重跑」。
3. **语义不清。** 「父 Run 重试」是重跑失败阶段还是全部阶段？两种理解的用户
   预期不同，本期不做这个歧义。

**采用**：子 Run 各自独立重试（它自己就是一个普通 Run），父 Run 的收敛规则
一行不改（spec FR-021）。若某阶段重试成功，链路自然继续推进到下一阶段。

## R-07 为什么复用既有 Redis 锁而不是新建重试锁

**候选方案**：为「重试调度」单独加一把 `retry:lock:{run_id}`。

**否定的理由**：两把锁会引入锁顺序问题（先拿哪个？拿不到对方怎么办？），
而重复执行的风险点只有一个——**同一时刻有两个执行体**。既有锁
`run:lock:{run_id}`（SET NX EX）已经精确覆盖这个风险：谁拿到谁执行，
后到者 `return "busy"`。

**采用**：复用。唯一需要补的是：`busy` 分支不能让这次触发凭空消失——
若因锁冲突未执行，按一次「未执行」处理（不入账、不计数），
等待下一次自然触发（手动重试或下一个重试周期）。这是安全的：
锁的 TTL（`_LOCK_TTL_SECONDS`）必然大于单次执行时长，所以不会出现
「永远拿不到锁」。

## R-08 重试参数为什么可配置而不是硬编码

**候选方案**：把 3 次、2 秒、60 秒写死在代码里。

**否定的理由**：不同 LLM 端点的抖动特征差别很大。自建的单机网关可能 1 秒就恢复，
跨区托管的网关可能要好几十秒。硬编码意味着换端点就要改代码重新发版。

**采用**：三个环境变量（上限 / 基准 / 封顶），默认值即 spec 假设值。
与 `SBX_TIMEOUT_DEFAULT` 等既有配置项同一风格。
