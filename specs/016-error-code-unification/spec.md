# Feature Specification: 错误码语义统一（016）

**Feature Branch**: `feat/016-error-code-unification`

**Created**: 2026-11-20

**Status**: Draft

**Input**: 用户 2026-11-20「逐个修复」——把 2026-11-17 审计与 README「已知限制」
里挂账两个月的**两套错误码并存**问题收敛掉：001/003/005 时代的老端点在
「非相关人访问」时回 403，007 之后的新端点回 404。

## 问题陈述

同一句「你不是这个资源的相关人」，在 API 上有两种回答：

| 端点世代 | 行为 | 后果 |
|---|---|---|
| 001 / 003 / 005 | `403 FORBIDDEN` | 攻击者可用 403 vs 404 的差异**枚举**资源 id：403 = 存在但不归你，404 = 不存在 |
| 007 / 008 / 009 / 010 | `404 NOT_FOUND` | 无法区分「不存在」与「无权」，不泄露存在性 |

这不是笔误，是**两个时期的安全判断不一致**：早期按「无权限」直觉返回 403，
007 起在分派场景里意识到可枚举问题，新端点改用 404，但按「不动既有契约」
的纪律没有回头改老端点，于是在 README 里挂成「已知限制」。

代价很实在：
1. 任何知道 or 猜得到 id 的人，都能用状态码差异确认「这个需求/Agent/组存在」；
2. 前后端各自维护两套「403 意味着什么」的判断；
3. 每次新增端点都要先问「我该跟哪一代」，答案每次都要回查 README。

## User Scenarios & Testing *(mandatory)*

### US1 — 陌生人访问他人资源得到「不存在」（优先级 P1）

作为平台，当用户 A 访问用户 B 的需求 / Agent / Agent 组 / 出网规则 /
外部工具安装时，响应必须是 404，**不能**因为「资源确实存在」而回 403。

**为什么这是用户故事而不是内部重构**：内部协作工具的定位是「B 等隔壁团队的 A」
（009 research R-05），用户群里有大量平级同事。能枚举「谁有多少需求、叫什么名字」
本身就是信息泄露。

**Acceptance Scenarios**：
1. **Given** B 有一个需求，**When** A（非创建者、非接收人、非项目成员）`GET /requests/{id}`，
   **Then** 404 `NOT_FOUND`，消息为「需求不存在」。
2. **Given** 同上，**When** A `PATCH` / `DELETE` / `POST .../assign`，
   **Then** 全部 404（不能只改读路径）。
3. **Given** B 有一个 Agent / Agent 组 / 出网规则，**When** A 读或改，
   **Then** 404。
4. **Given** B 安装了外部工具，**When** A 尝试升级 / 吊销该安装或凭证，
   **Then** 404。
5. **Given** A 访问一个**格式合法但不存在**的 id，**Then** 404，且响应体与
   「存在但不归你」**完全一致**（同 code、同 message、同结构）。

### US2 — 参与者权限不足仍然是 403（优先级 P1）

404 只用于「你和这个资源无关」。已经知道资源存在、但缺少**某个字段或动作**的权限时，
必须继续回 403，否则用户会以为资源被删了。

**Acceptance Scenarios**：
1. **Given** viewer 角色，**When** 调用任何 member/admin 端点，**Then** 403
   （角色不足，与资源无关）。
2. **Given** 我是项目成员但非 owner，**When** 管理项目成员，**Then** 403。
3. **Given** 我经手过一个需求（assignee），**When** 改它的 `project_id`，
   **Then** 403（我知道它存在，只是没这个字段的权限）。
4. **Given** 我是 admin 在查看他人调度，**When** 尝试修改，**Then** 403。
5. **Given** 内置 Agent 模板（`owner_id IS NULL`），**When** 任何用户编辑或删除，
   **Then** 403（模板对所有人可见，不存在泄露问题）。

### US3 — 契约与文档只有一个答案（优先级 P2）

`specs/*/contracts/api.md` 与 README 的「已知限制」不再描述两套口径；
新端点无需再查历史。

**Acceptance Scenarios**：
1. 10 份 contracts 中涉及「非相关人」的条目统一为 404。
2. README「已知限制」里那条「两套并存」被删除，替换为一条统一口径说明。

### Edge Cases

- **认证失败**：无 token / token 失效 → 401，不属于本特性范围（未认证不谈资源）。
- **非法 UUID**：`/requests/not-a-uuid` → 422（deps 的 `_resource_id` 校验），
  不是 404。格式错误与「不存在」是两件事。
- **被删除的资源**：软删/归档后 → 404，与「不归你」同响应。
- **管理员**：admin 读他人资源是否放行由各端点既有策略决定，**本特性不改**；
  只改「非相关人」的状态码。
- **WS 通道**：`/ws/runs/{id}` 的拒绝是 close code 1008，不是 HTTP 状态码，
  本特性不动。

## Requirements *(mandatory)*

### 功能需求

- **FR-001**：需求的单条读写（详情/更新/删除/分配/依赖边/附件/接受/拒绝）
  对**非相关人**一律 404。相关人 = 创建者 ∪ 当前接收人 ∪ 项目成员（010）。
- **FR-002**：Agent 的读/改/删/归档/克隆对**非 owner** 一律 404。
- **FR-003**：Agent 组的读/改/删/成员管理对**非 owner** 一律 404。
- **FR-004**：Agent 出网规则的读写对**非 Agent owner** 一律 404。
- **FR-005**：外部工具安装、凭证、授权的操作对**非本人**一律 404。
- **FR-006**：把一个**他人的 Agent** 加入自己的组 → 404（不暴露该 Agent 存在）。
- **FR-007**：以下场景**保持 403**，不得改：viewer 角色守卫；项目成员做 owner 动作；
  内置模板编辑/删除；admin 修改他人调度；assignee 改 `project_id`；登录失败。
- **FR-008**：相关人与非相关人的响应体必须**逐字节同构**（同一个 `error.code`、
  同一个 `message`），不允许 message 里出现「无权限」这类暗示。
- **FR-009**：`specs/001` `003` `005` 的 contracts 与 README「已知限制」同步更新。

### 非功能需求

- **NFR-001**：只改状态码与 message，**不改**任何业务逻辑、事务边界、审计写入。
- **NFR-002**：全量测试与覆盖率门禁（`fail_under=85`）保持通过。
- **NFR-003**：前端不改逻辑——前端没有基于 403 做需求页跳转，错误消息由
  ErrorBanner 直通展示。

## Success Criteria *(mandatory)*

- **SC-001**：`grep -rn 'AppError("FORBIDDEN"' backend/app/services` 的结果里，
  不再有「非相关人访问」语义的条目（只剩 FR-007 白名单里的）。
- **SC-002**：全量测试通过，且**新增**至少 6 个「陌生人 → 404」的正向断言
  （每类资源一个）。
- **SC-003**：同一资源「不存在」与「存在但不归你」两次请求的响应体 JSON 相等。
- **SC-004**：README「已知限制」不再出现「两套并存」。

## Out of Scope

- 不改 401 / 422 / 409 / 429 的语义。
- 不引入「资源存在性掩码」之类的新机制——404 就是掩码。
- 不动 WebSocket 的 close code。
- 不改 admin 的越权读策略（那是产品决策，不是编码一致性问题）。

## Assumptions

- 平台无公开 API 消费者，改状态码不会破坏第三方集成。
- 前端唯一依赖 403 的地方是**角色守卫**（viewer 进 admin/模板/调度页），
  与资源归属无关，因此不需要改。
