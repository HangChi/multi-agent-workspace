# Research: 012 错误消息直通

编号 `R-01…`。每条写**决策 / 依据 / 被否决的方案及理由**。

## R-01：修在组件一处，不改 19 个调用方

- **决策**：`ErrorBanner` 加一行判型（`typeof error === 'string'` 直通），
  19 个调用方一律不动。
- **依据**：实测 2026-11-18（011 的 s12 诊断）——19 处调用点的入参分两类：
  ① `useState<string | null>` + `setError(extractError(err))` 传**已提取
  字符串**（18 处）；② 字面量字符串（`MarketplacePage` 的「工具市场加载
  失败…」、`DashboardPage` 的「统计加载失败」）。两类都过同一个组件。
  在组件处判型，一处覆盖全部；改调用方要动 19 个文件，且每个都要回归。
- **被否决**：① 把 19 个调用方改成传原始错误（`setError(err)`）——
  state 类型要从 `string | null` 放宽到 `unknown`，所有 `error &&` 判断
  的语义跟着变（truthy 的对象 vs 字符串），回归面 19 处；② 在
  `extractError` 里加字符串直通——那个函数的契约是「从错误对象提取」，
  它的单测（client.test.ts 四条）钉的就是这个；让它认字符串是把两个
  关注点搅在一起，且 `extractError('')` 该返回什么更含糊。

## R-02：保留调用方「先 extract 再入 state」的模式

- **决策**：不动调用方的 `setError(extractError(err))`。
- **依据**：这个模式本身有好处——state 是 `string | null`（简单、可
  序列化、可断言），错误在入库的**边界**（mutation onError）就完成提取，
  组件只负责显示。它不是 bug；bug 单点在于组件假设入参一定是错误对象。
- **被否决**：把提取推迟到组件（调用方 `setError(err)` 传原始错误）——
  见 R-01 ①，回归面 19 处且 state 类型退化。

## R-03：空字符串按「无错误」处理

- **决策**：`error=''` 不渲染（复用现有 `if (!error) return null` 的
  falsy 短路）。
- **依据**：空字符串没有可显示的内容；调用方的模式是「无错误时
  `setError(null)`」，空串只会来自笔误，渲染一个空横幅比不渲染更怪。
- **被否决**：空串渲染成兜底文案——把一个「没有消息」的状态谎报成
  「请求失败」，正是这个特性要消灭的行为。

## R-04：docstring 即契约——两种形态都写进文档

- **决策**：组件 docstring 明确「既收原始错误对象（组件提取），也收
  已提取消息字符串（直通）」，各给示例。
- **依据**：这次 bug 的远因就是契约只写了一半（原文只说「错误消息统一
  经 extractError() 提取」）。19 个调用方按另一半直觉（state 存字符串）
  全中了坑。文档补全 + 单测钉住，下一代维护者不会再犯。
- **被否决**：只改代码不写文档——同样的坑三年前（T082）就埋过，
  不写清契约等于再埋一次。
