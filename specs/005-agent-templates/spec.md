# Feature Specification: Agent 模板与一键克隆（把调好的 Agent 变成可复用的起点）

**Feature Branch**: `feat/005-agent-templates`
**Created**: 2026-11-18
**Status**: Draft
**Input**: User description: "005：Agent 模板 / 一键克隆。001-004 已完成。现在每建一个 Agent 都要从零填表单（提示词、模型、温度、步数、工具、成本上限），调好的配置想复用只能照着抄；希望把 Agent 配置沉淀成模板，一键创建或一键克隆。"

## 背景与动机

001–004 已经把「需求 → 分配 → 执行 → 调度」的闭环建完整，但 **Agent 的创建成本始终是最高的那一道门槛**：要写系统提示词、选模型、调温度、定步数与成本上限、勾工具集、决定出网模式。一个调教到位的 Agent 往往要反复试跑多轮才能稳定，而这些经验全部沉淀在**某一个人的某一次填写里**，无法传递给下一个人、下一个场景、下一台部署。

结果是两种浪费：

- **重复劳动**：同一个角色（代码审查、数据摘要、客服问答）每次使用都要重填一遍表单，抄漏一个字段就要再试跑一轮才能发现。
- **经验不可继承**：团队里调得最好的那个提示词只存在于某个 Agent 里，新成员看不到、学不走、改不动。

本特性为工作台补上**配置复用层**：把 Agent 的完整配置沉淀为**模板**，支持从模板一键创建、从已有 Agent 一键克隆、把调好的 Agent 另存为模板，并预置若干**内置模板**让新部署开箱可用。

**核心设计取舍（已与用户确认）**：

- **模板是快照，不是引用**。从模板创建的 Agent 是**完全独立的副本**，之后修改模板不会传染已创建的 Agent；反过来修改 Agent 也不会改写模板。引用式复用会让「改一个模板，十个 Agent 同时变脸」，排障与成本核算都会失真——这与 004「修改调度不改写已产生需求」（FR-020）是同一条纪律。
- **克隆不复制实例级数据**。克隆只复制配置字段；运行历史、步骤、制品、组引用、外部工具授权、出站规则全部不复制。授权与规则涉及凭证与既有事实，复制它们会造成「看起来配好了、跑起来才失败」的假象。
- **内置模板由种子脚本按当前 LLM 端点注入**，而不是把模型名硬编码进迁移。迁移不导入应用代码（本仓库既有约定），且内置模板的模型必须跟随 `LLM_MODEL` 才可能在当前端点真正可用。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从模板一键创建 Agent (Priority: P1)

成员打开 Agent 页，选择「从模板创建」，看到模板列表（内置模板 + 自己的模板），每个模板展示名称、描述、模型、工具与适用场景。选中后表单被**预填**为模板配置，成员仍可修改任何字段再保存，也可以直接一键确认。

**Why this priority**: 这是特性对普通成员的直接价值——把「建 Agent」从一次需要想清楚所有参数的创作，降级为一次选择题。

**Independent Test**: 用一个内置模板创建 Agent，验证产物的每个配置字段与模板一致；再改用模板后手动改两个字段保存，验证只有这两个字段不同，其余仍与模板一致。

**Acceptance Scenarios**:

1. **Given** 成员打开「从模板创建」，**When** 列表加载完成，**Then** 能看到至少一个内置模板与自己的模板，每个都展示名称、描述、模型、已选工具。
2. **Given** 成员选中一个模板，**When** 表单打开，**Then** 名称、描述、系统提示词、模型、温度、最大步数、超时、成本上限、工具集、出网模式全部预填为模板值，且均可编辑。
3. **Given** 成员直接用模板值保存，**When** 创建成功，**Then** 新 Agent 的上述字段与模板**逐字段一致**，且不产生任何运行历史。
4. **Given** 成员把模板的温度与工具集改掉后保存，**When** 创建成功，**Then** 新 Agent 只有这两个字段与模板不同，其余字段仍与模板一致。
5. **Given** 模板引用的某个工具已在模板创建后被下线，**When** 成员用该模板创建 Agent，**Then** 创建**成功**，该工具被从工具集中过滤，并给出可读提示指明被过滤的工具名，MUST NOT 因工具失效而创建失败。

---

### User Story 2 - 一键克隆已有 Agent (Priority: P1)

成员在自己的 Agent 卡片上点「克隆」，立即得到一个配置完全相同、名称为「{原名} 副本」的新 Agent，可随后改名改配置。克隆不复制运行历史，也不影响原 Agent 的任何数据。

**Why this priority**: 「想微调一个已经跑顺的 Agent」是最频繁的复用场景（改个温度、换个模型做 A/B），手动重抄一份是纯浪费。

**Independent Test**: 克隆一个被组引用、有外部工具授权、有已完成运行的 Agent，验证新 Agent 的 8 个配置字段与源一致，新 Agent 运行数为 0，源 Agent 的组引用数、授权数、运行数均不变。

**Acceptance Scenarios**:

1. **Given** 成员有一个配置完整的 Agent，**When** 执行克隆，**Then** 立即产生一个同配置的新 Agent，默认名称为「{源名称} 副本」，源 Agent 的全部字段不变。
2. **Given** 源 Agent 已被某个组引用且已有运行历史，**When** 克隆，**Then** 新 Agent 不在任何组中、运行历史为空，源 Agent 的组引用与运行历史保持原样。
3. **Given** 成员连续克隆同一个 Agent 两次，**When** 第二次执行，**Then** 新名称不与第一次克隆结果冲突（追加可区分的后缀），两个克隆体可同时存在。
4. **Given** 源 Agent 的出网模式为限制模式但尚无启用的允许规则，**When** 克隆，**Then** 克隆**成功**，且响应中携带与既有 Agent 保存一致的警告（限制模式下无允许规则，运行时全部出站被拒）。
5. **Given** 成员对他人 Agent 执行克隆，**When** 提交，**Then** 返回不存在或无权访问，不泄露该 Agent 的存在性。

---

### User Story 3 - 把调好的 Agent 另存为模板 (Priority: P1)

成员把一个已经跑顺的 Agent 保存为自己的模板，沉淀名称、描述与完整配置；之后源 Agent 的修改不影响模板，模板的修改也不影响源 Agent。

**Why this priority**: 没有「沉淀」这一环，模板只能来自内置，无法积累团队自己的经验，特性的长期价值就断了。

**Independent Test**: 从 Agent A 另存为模板 T，然后修改 A 的两个字段并修改 T 的两个字段，验证 A 与 T 互不影响，且 T 仍可用 US1 的方式创建出与 T 当前配置一致的 Agent。

**Acceptance Scenarios**:

1. **Given** 成员有一个 Agent，**When** 执行「另存为模板」，**Then** 生成一个属于该成员的模板，配置字段为保存时刻的**快照**。
2. **Given** 模板已生成，**When** 成员修改源 Agent 的任意字段，**Then** 模板内容不变。
3. **Given** 模板已生成，**When** 成员修改模板的任意字段，**Then** 源 Agent 与已由该模板创建的 Agent 均不变。
4. **Given** 成员已有同名模板，**When** 再次另存，**Then** 系统拒绝并给出可读原因（模板名在同一所有者下 MUST 唯一），MUST NOT 静默覆盖。
5. **Given** 源 Agent 已被归档，**When** 执行另存为模板，**Then** 仍允许保存（归档不影响配置的复用价值），模板不含任何归档状态语义。

---

### User Story 4 - 模板管理 (Priority: P2)

成员能查看、编辑、删除自己的模板；内置模板只读。删除模板不影响已由它创建的 Agent。

**Why this priority**: 模板会随认知演进而过时，不能删除的模板库会迅速堆积噪音，把「从模板创建」的选择成本重新推高。

**Independent Test**: 创建一个模板并用它创建 Agent A，然后删除该模板，验证删除成功、A 完全不受影响；再验证内置模板不可编辑、不可删除。

**Acceptance Scenarios**:

1. **Given** 成员有若干自己的模板，**When** 打开模板管理，**Then** 能看到自己的模板列表与内置模板列表，且两者的可操作性明显区分。
2. **Given** 成员编辑自己的模板，**When** 保存，**Then** 更新成功，已由它创建的 Agent 配置不变。
3. **Given** 成员删除自己的模板，**When** 删除完成，**Then** 模板不再出现在任何模板列表中，由它创建的 Agent 全部保留且可正常运行。
4. **Given** 成员尝试编辑或删除一个内置模板，**When** 提交，**Then** 系统拒绝并说明内置模板只读。
5. **Given** 成员访问他人的模板，**When** 查看、编辑或删除，**Then** 返回不存在或无权访问，措辞与「模板不存在」一致。

---

### User Story 5 - 新部署开箱可用 (Priority: P2)

一次全新部署（空库）在完成迁移与种子注入后，成员打开「从模板创建」即可看到若干覆盖常见场景的内置模板，无需先自己造一个 Agent。

**Why this priority**: 内置模板是特性的冷启动。没有它们，新用户的第一个 Agent 仍然要从零写提示词，特性的入门价值减半。

**Independent Test**: 在空库上执行迁移 + 种子脚本，验证内置模板数量 ≥ 3、均归属于系统、所有成员可见、均不可写，且其中至少一个的模型与当前 `LLM_MODEL` 一致。

**Acceptance Scenarios**:

1. **Given** 空库完成迁移与种子注入，**When** 任一成员打开模板列表，**Then** 能看到全部内置模板。
2. **Given** 内置模板存在，**When** 任一成员尝试修改或删除，**Then** 被拒绝。
3. **Given** 部署更换了 LLM 端点，**When** 重新执行种子脚本，**Then** 内置模板的模型更新为新的 `LLM_MODEL`，其余配置不变，且不产生重复模板（脚本 MUST 幂等）。
4. **Given** 种子脚本重复执行多次，**When** 每次执行完成，**Then** 内置模板数量不变、无重复行。

---

### Edge Cases

- **模板引用的工具在创建时已下线**：创建 MUST 成功并过滤该工具 + 可读提示；MUST NOT 让一次工具下线就废掉一个模板。
- **模板引用的模型在当前端点不存在**：模板不绑定「模型一定可用」的承诺；创建时按现有契约接受该模型名（与手工创建同语义），失败发生在执行期而不是创建期。内置模板的模型则由种子脚本跟随 `LLM_MODEL` 保证可用。
- **克隆时源 Agent 恰好被并发删除**：克隆 MUST 返回不存在或无权访问，MUST NOT 产生引用悬空配置的克隆体。
- **同一所有者下模板名重复**：拒绝 + 可读原因；MUST NOT 静默覆盖已有模板。
- **克隆同名累积**：连续克隆 MUST 产生可区分的名称，MUST NOT 因名称撞车而失败。
- **源 Agent 处于归档态**：克隆与另存为模板 MUST 仍可用（归档只影响可分配性，不影响配置复用价值）；但用模板创建的新 Agent MUST 是活跃态。
- **模板所属用户被删除**：其模板随用户级联删除（与 schedules 的 `ondelete=CASCADE` 一致），已创建的 Agent 保留。
- **内置模板被用户「另存为模板」**：MUST 生成一个属于该用户的可编辑副本，MUST NOT 试图修改内置模板本身。
- **system_prompt 为空或超长**：与既有 Agent 创建契约同一套校验（必填、长度上限），MUST NOT 出现模板能存、Agent 不能建的错配。
- **从模板创建时用户改坏了必填字段**：前端与后端同一套校验，后端 MUST 独立拒绝，不依赖前端。

## Requirements *(mandatory)*

### Functional Requirements

**模板的创建与沉淀**

- **FR-001**: 系统 MUST 允许成员把任意归属自己的 Agent 的完整配置（名称、描述、系统提示词、模型、温度、最大步数、单次运行超时、工具集、成本上限、出网模式）另存为自己的模板，保存内容 MUST 是保存时刻的**快照**。
- **FR-002**: 系统 MUST 保证模板与源 Agent 的双向隔离：保存后修改源 Agent MUST NOT 改写模板；修改模板 MUST NOT 改写源 Agent 或任何已由该模板创建的 Agent。
- **FR-003**: 系统 MUST 拒绝同一所有者下的重名模板，并返回可读原因；MUST NOT 静默覆盖。
- **FR-004**: 模板 MUST 遵循既有资源归属校验：成员只能查看、编辑、删除自己的模板；访问他人模板时 MUST 返回与「模板不存在」一致的措辞，MUST NOT 泄露资源存在性。

**从模板创建 Agent**

- **FR-005**: 系统 MUST 提供「从模板创建」入口，创建时表单 MUST 以模板配置预填且允许修改任意字段。
- **FR-006**: 系统 MUST 支持不修改任何字段的一键创建，产物与模板配置**逐字段一致**。
- **FR-007**: 从模板创建的 Agent MUST 是全新独立实体：运行历史、组引用、外部工具授权、出站规则均为空或未配置，MUST NOT 从模板继承任何实例级数据。
- **FR-008**: 模板引用的工具在创建时已下线或未启用时，系统 MUST 从工具集中过滤该项并随响应返回可读提示（指明被过滤的工具名），MUST NOT 因此创建失败。
- **FR-009**: 从模板创建 MUST 经过与手工创建完全相同的校验（必填、长度、数值范围、工具白名单、出网模式取值），MUST NOT 存在模板专属的宽松路径。

**克隆已有 Agent**

- **FR-010**: 系统 MUST 支持对归属自己的 Agent 执行一键克隆，产物复制源 Agent 的全部配置字段，默认名称为「{源名称} 副本」。
- **FR-011**: 克隆 MUST NOT 复制任何实例级数据：运行、步骤、制品、组成员关系、外部工具授权、出站规则。
- **FR-012**: 当源 Agent 出网模式为限制模式且无启用的允许规则时，克隆 MUST 成功，且响应 MUST 携带与既有 Agent 保存接口一致的警告文案。
- **FR-013**: 连续克隆 MUST 产生互不冲突的名称（追加可区分后缀），MUST NOT 因名称冲突失败；被组引用的源 Agent MUST 允许克隆。
- **FR-014**: 克隆归档态 Agent MUST 允许；产物 MUST 为活跃态。

**内置模板与种子**

- **FR-015**: 系统 MUST 提供覆盖常见场景的内置模板（≥ 3 个），归属于系统，对所有成员可见且**只读**（编辑、删除 MUST 被拒绝）。
- **FR-016**: 内置模板的注入 MUST 是幂等的：重复执行 MUST NOT 产生重复模板或改变模板数量。
- **FR-017**: 内置模板的模型 MUST 来自部署当前的 LLM 配置，MUST NOT 把某个特定模型名硬编码进数据库迁移。
- **FR-018**: 任一成员 MUST 能把内置模板另存为自己的模板，产物 MUST 属于该成员且可编辑。

**安全与审计**

- **FR-019**: 模板的创建（另存为模板）、修改、删除，以及从模板创建、克隆 Agent，MUST 全部写入既有审计记录，至少包含操作者、时间、动作、目标与来源（模板或源 Agent）。
- **FR-020**: 克隆与模板创建 MUST NOT 扩大操作者权限：产物只包含配置字段，MUST NOT 携带源 Agent 的凭证、授权或任何实例级凭据。
- **FR-021**: 删除模板 MUST NOT 级联删除已由它创建的 Agent；删除 Agent MUST NOT 删除由它产生的模板。
- **FR-022**: 模板服务 MUST NOT 成为绕过 Agent 既有校验的旁路：所有经模板产出的 Agent MUST 满足与手工创建同一套不变量（工具白名单、成本上限下限、出站模式取值）。

### Scope Boundaries *(explicit exclusions)*

- **不含** 模板的跨用户共享、发布、市场或权限授予（003 的「市场」指外部 MCP 工具市场，Agent 模板市场不在本特性范围；模板库是**个人私有**的）。
- **不含** 模板版本历史与差异对比；模板只有当前快照，改坏了就重新另存。
- **不含** 克隆/模板对外部工具授权（external tool grants）与出站规则（egress rules）的复制；这些需用户在产物上重新配置。
- **不含** 「从模板批量创建多个 Agent」与「模板驱动的 Agent 组」。
- **不含** 模板导入导出（JSON/YAML 文件）与跨部署迁移。
- **不含** 模板使用统计（「这个模板被用了几次」）与推荐排序。
- **不含** 调度与模板的联动（004 的规则仍指向具体 Agent/组，不指向模板）。

### Key Entities *(include if feature involves data)*

- **Agent 模板（AgentTemplate）**: 一段可复用的 Agent 配置快照。含名称、描述、系统提示词、模型、温度、最大步数、单次运行超时、工具集、成本上限、出网模式，以及归属与内置标志。`owner_id` 为空表示内置模板。
- **Agent（既有实体）**: 新增「来源模板」可选关联，仅用于追溯「这个 Agent 是用哪个模板建的」；不改变其既有字段语义与生命周期。克隆产物同样记录来源（源 Agent）。
- **克隆产物**: 一个普通的、活跃的 Agent，配置等于源 Agent，实例级数据为空。它不是新实体，只是既有 Agent 的一种产生方式。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在有现成模板的前提下，从打开模板列表到完成创建，95% 的操作可在 **3 步、30 秒**内完成（打开列表 → 选模板 → 确认），零必填项需要重新输入。
- **SC-002**: 一键克隆产物的 8 个配置字段（描述、系统提示词、模型、温度、最大步数、单次运行超时、工具集、成本上限）与源 Agent **100% 一致**（名称按 FR-010 规则派生，不计入）。
- **SC-003**: 克隆与「从模板创建」产物的运行历史条数为 **0**、组成员关系数为 **0**、外部工具授权数为 **0**、出站规则数为 **0**。
- **SC-004**: 修改或删除模板后，由该模板创建的 Agent 的配置字段被改写条数为 **0**。
- **SC-005**: 模板引用已下线工具的创建场景中，创建成功率为 **100%**，被过滤工具在响应提示中出现的覆盖率为 **100%**（无静默丢弃）。
- **SC-006**: 越权访问（查看/编辑/删除/使用）他人模板的请求，**100%** 返回与「模板不存在」一致的响应，无存在性泄露。
- **SC-007**: 另存为模板、模板修改、模板删除、从模板创建、克隆 五类动作的审计覆盖率 **100%**，抽查记录不含凭证原文。
- **SC-008**: 内置模板相关断言：空库种子后内置模板数 ≥ 3 且全部只读，重复执行种子脚本后模板数不变（增量 **0**）。
- **SC-009**: 克隆被组引用的 Agent 后，源 Agent 的组成员关系数变化为 **0**。

## Assumptions

- **模板是个人私有的**：不做共享/市场（与 003 的「外部工具市场」是两回事）。后续若确需团队级模板库，作为独立特性扩展，不在本特性预留半成品。
- **工具白名单以工具目录为单一事实源**：与既有 `AgentCreate` 一致，模板中的 `tools` 只在创建/保存时按目录校验与过滤，不缓存「某工具曾可用」的事实。
- **模型可用性不前置校验**：与手工创建同语义——契约层接受任意 ≤100 字符的模型名，可用性由执行期决定。内置模板例外，其模型由种子脚本取 `LLM_MODEL`，从而跟随端点。
- **克隆名称规则**：`{源名称} 副本`，若已存在则追加 ` 副本2`、` 副本3`…（上限由名称长度 100 字符约束，超出时截断基名）。
- **另存为模板的默认名**：`{源 Agent 名称}`；与既有模板重名时拒绝（FR-003），由用户改名，而不是自动加后缀——避免模板库出现一堆「XX 副本」噪音。
- **内置模板数量与内容**：种子脚本注入 4 个覆盖「通用问答 / 代码审查 / 数据摘要 / 资料检索」的模板；提示词质量以「可直接跑出可用结果」为标准，具体文案在实现阶段定稿并评审。
- **删除语义**：删除模板是硬删（无软删/回收站），与既有 Agent 删除语义一致；已创建的 Agent 不受影响（FR-021）。
- **审计动作命名**：沿用既有 `<域>_<动作>` 风格，新增 `agent_template_create` / `agent_template_update` / `agent_template_delete` / `agent_create_from_template` / `agent_clone`。
