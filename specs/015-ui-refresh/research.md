**Feature**: `015-ui-refresh` | **Date**: 2026-11-19

> 记录本特性的关键技术取舍与**做错的判断**。每条格式：决策 / 理由 /
> 被否方案 / 代价。

## R-01 规格先行的偏离与代价（流程，最重要的一条）

**决策**：按用户「逐个模块改、及时提交」的指令，先实现后补规格。

**理由**：用户明确要求以模块为单位连续提交，逐个评审；停下来先写九件套
会打断这个节奏。

**代价（实测发生，不是假设）**：

1. `specs/015-*` 缺失两周期的后果——`.specify/feature.json` 仍指向 014，
   下次开工时「上一个特性收尾了吗」的判断依据是错的（这正是 006/007
   踩过的同一个坑：实现已合并但流程记录没跟上）。
2. **没有 spec 就没有验收清单**，于是没人提醒「改完要跑 s12」——UI 改了
   依赖弹层的移除交互（加二次确认），走查脚本没跟，s12 从 15/15 掉到
   13/15，直到 015 补记这天跑一遍才发现。
3. 逐模块提交时只跑了 `tsc` / `eslint` / `vitest` 三门禁，**没跑
   `prettier --check`**（它不在当时的提交前习惯里），24 个文件格式漂移，
   把 CI 的前端 job 整条卡死。

**纠正**：

- 本目录补记 spec / plan / research / tasks / quickstart（按实际提交与实测
  反推，不虚构决策过程）。
- 提交前门禁补上 `format:check`（与 CI 同口径，见 quickstart §2）。
- 改动触及 008/009/010 的交互时，`s12_browser_walkthrough.py` 必须同批跑
  并同步脚本。

**被否方案**：不补记、直接开 016。否决理由：那样 015 会永久是一段没有
FR/SC 的黑箱，README 特性表也没法写它。

## R-02 焦点陷阱自研，不引 `focus-trap-react`

**决策**：`hooks/useFocusTrap.ts` 自己实现 Tab 循环、焦点归还、滚动锁。

**理由**：需求里有三条现成库要额外包裹才能满足的行为——

1. **弹层栈**：命令面板与 Modal 可能同时存在，Esc 只关栈顶（库通常只保证
   单实例隔离）。
2. **滚动条宽度补偿**：`overflow: hidden` 会让页面横向跳一下，需要
   `padding-right = scrollbarWidth`。
3. **`initialFocus` 传 ref 而非选择器**：要与 React 的挂载时机对齐，
   自己 rAF focus 会和 hook 的 `panel.focus()` 抢，且初期实测抢输了。

**被否方案**：`focus-trap-react` + 自建滚动锁。否决理由：两套机制各自
维护「谁是栈顶」，行为冲突比自研更难查。

**代价**：约 120 行自有代码需要自己保证正确性；用组件测试钉住（Modal 与
CommandPalette 共用同一实现，任一处回归都会红）。

## R-03 Agent 配置区：组合，不复制

**决策**：抽 `AgentConfigFields` + `useToolsCatalog` + `constants.ts`，
AgentForm 与 TemplateForm 共用。

**理由**：两处表单 170 行几乎逐字重复，差异只有「是否允许从模板创建」与
提交目标。重复的代价不是行数，是**改一处忘另一处**——工具目录三态
（加载/空/错误）就是在其中一份里漏掉的。

**被否方案**：给重复块加注释「改动请同步另一处」。否决理由：这种注释
在仓库里从来没被遵守过。

## R-04 表单切换用 `key` 重挂载，不用 `useEffect` 重置

**决策**：`<AgentForm key={editing?.id ?? 'new'} />`。

**理由**：`useState(initialValue)` 的初始化器只在首次挂载跑。连点两个
「编辑」，第二个表单拿到的仍是第一个对象的 state——这不是「显示旧值」，
是**提交时把 A 的内容写到 B 名下**的静默数据损坏。

**备选**：`useEffect(() => setForm(toForm(editing)), [editing])`。否决理由：
每个字段都得重置，漏一个就是同一个 bug 的变种；`key` 把「重置」这件事
交给 React 的挂载语义，没有遗漏面。

**代价**：重挂载会丢失未提交的草稿（可接受：切对象本来就是放弃草稿）。

## R-05 乐观更新按 query key 前缀快照

**决策**：`getQueriesData({ queryKey: ['requests'] })` 逐条快照 → 就地改写
→ 失败回滚。

**理由**：看板的 key 组合有三个维度（`scope=mine|relevant` × `project_id`
× 搜索词）。原实现硬编码 `['requests','relevant']`，于是：`scope=mine` 时
用户看不到任何反馈（像没生效），且写到了一条界面上根本没人看的缓存里。

**被否方案**：`invalidateQueries` 不做乐观更新。否决理由：拖拽是高频
交互，等一次网络往返再动卡片，手感差一档；且拖拽回弹比「卡片先动后回滚」
更让人困惑。

## R-06 z-index 用语义令牌，不用「谁大谁赢」

**决策**：`header(40) / sticky(30) / dropdown(50) / modal / toast` 语义分层，
页面内吸顶工具条统一 `z-sticky`。

**理由（实测踩坑）**：头像下拉在 Topbar 内部用 `z-dropdown(50)`，看似比
任何东西都高；但 Topbar 是 `z-header(40)` 的定位元素——**独立层叠上下文**，
子元素的 50 被整体封在 40 里。看板工具条同样 40、DOM 顺序在后，于是
凭「后者居上」把整个 Topbar 盖住。

教训写成一句话：**跨容器比较 z-index，必须看「最近的有 z-index 的祖先」，
不是自己的数值。** 语义令牌把「该属于哪一层」显式化，避免下次再靠调大
数字打补丁。

## R-07 视觉提质：层次与品牌色，不是换色板

**决策**：明度差（canvas 加深一档）+ 三层阴影（card / lift / glow）+
品牌表面令牌 `--surface-brand`。

**理由**：用户反馈「还是丑」时，第一反应是换配色方案——但截图诊断显示
病灶是**没有层次**：卡片白、页面白、边框 1px 浅灰，三者明度差只有 5，
整页是一片糊。换任何色板都救不了「所有东西都一样平」。

「不丑」的最低门槛是：**能看出前后关系**（阴影 + 明度差）与**有一处
克制的品牌色**（激活态、主按钮）。装饰性的圆角/渐变/动效都不解决这个问题。

**反向教训**：头像全用同一个蓝渐变，一排七八个芯片像同一块砖复制——改成
按 id 散列到五套柔和渐变后，「可区分」这件事才成立。

## R-08 不引入常驻 e2e，复用 s12 一次性脚本（附代价）

**决策**：仓库仍不建 Playwright e2e 常驻基建；浏览器验证靠 s12 一次性脚本
+ 手工冒烟。

**理由**：s12 已经在真实栈上跑 008/009/010 的 15 项清单，是现成的资产；
再引一套 e2e 框架意味着接线、种子数据、CI 时长一整套投入，收益重叠。

**代价（本轮实测发生）**：s12 是「脚本跟着 UI 走」，不是「UI 跟着脚本走」。
015 给移除前置依赖加二次确认后脚本没同步，s12 掉到 13/15（B1 卡在等弹层
消失、B2 的前置数从 1 变 2）。修复=脚本补点确认框那一下。

**纠正**：把「改了 008/009/010 的交互就跑 s12 并同步脚本」写进 tasks.md
的收尾项，而不是留在口头纪律。
