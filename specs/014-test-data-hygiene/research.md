# Research: 014 测试数据卫生

## R-01：删除必须「污染传播 + 拓扑排序」两阶段，不能只按用户列删

- **决策**：阶段一从受害用户沿 FK 图向下不动点迭代，算出每张表的污染行
  id 集；阶段二按子→父拓扑序删。
- **依据**：前两版实现的失败实录——① 只收 roots 的「祖先」没收「后代」，
  删 agent_groups 被 group_members 挡住（FK 违约，事务回滚）；  ② 改成
  按用户列删，group_members 根本没有用户列，永远碰不到。第三版才意识到
  `group_members` 是「用户 → agent_groups → group_members」传播链的中间
  节点，必须按传播算而不是按列算。
- **被否决**：手写表序——21+ 张表加自引用/环，手写必漏；TRUNCATE 全表
  ——会连真实账号的数据一起删。

## R-02：不动点迭代而非 BFS 分层

- **决策**：污染集用不动点迭代（直到没有集合增长），不用按 FK 距离分层。
- **依据**：FK 图里同层可以有边——`runs.owner_id → users` 与
  `runs.request_id → requests` 让 runs 和 requests 同距 users，分层
  BFS 在同层内顺序不定，可能漏算「owner 不是受害者但 request 是」的行。
- **被否决**：BFS 分层——第二版的删除序把 requests 排在 runs 前，
  FK 直接违约。

## R-03：FK 环与自引用的处理

- **决策**：`users.invite_code_id → invite_codes` + `invite_codes.created_by
  → users` 成环——执行时先把受害者该列置 NULL 破环；删 invite_codes 时
  排除仍被保留用户引用的行。自引用（`runs.parent_run_id`、
  `agents.source_agent_id`）在拓扑排序中忽略。
- **依据**：环让拓扑排序无解（第一版 RuntimeError）；自引用删行即删关系，
  参与排序只会制造假环。实测无「保留行引用受害行」的边案（查询计数为 0）。
- **被否决**：`SET session_replication_role = replica` 关 FK 触发器——
  能删但会留下孤儿行，把问题藏起来；本工具要的是「删完数据库仍然自洽」。

## R-04：面板重设计——三行分区 + 折叠 + 过滤，不动拖拽契约

- **决策**：同事/Agent/组各占一行（各带计数），每行默认露 8 个 + 「+N
  展开」，同事行加邮箱过滤框；`useDroppable` 的 id 与 title 逐字保留。
- **依据**：旧版三类混在一行横滚——注释里写着「分块展示」实际只加了根
  分隔线。账号 300+ 时那行是永远滚不到头的墙，「这里能拖」被淹没。
  数据清理（R-01~03）解决存量，分区+折叠+过滤解决增量（验收脚本还会
  继续建账号）。title 不变是为了 s12 的 B4（`[title*='拖到这里分配给']`）
  和一切依赖拖拽提示的既有行为。
- **被否决**：虚拟滚动——为一排 32px 芯片引入虚拟化是杀鸡用牛刀；
  改成下拉选择器——丢掉拖拽语义（007 的核心交互就是拖）。
