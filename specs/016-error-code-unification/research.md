# Research: 016 错误码语义统一

每个决策记录「为什么更简单的做法不行」，避免三个月后有人凭直觉回改。

## R-01 为什么用 404，而不是继续 403 + 更严格的权限

**备选**：保留 403，靠「不告诉前端资源是否存在」来缓解。

**为什么不行**：状态码本身就是信息。403 与 404 的差异是**协议层**的，
不需要任何业务字段就能读出「这个 id 存在」。攻击者遍历 UUID 的代价很高，
但内部威胁模型里最常见的不是遍历，而是**已知 id**（从聊天记录、截图、日志、
导出的表格里拿到的）。对已知 id，403 直接确认「你没权限但它在」。

**结论**：404 是「不暴露存在性」的标准做法，也是 007 起已在新端点上验证过的做法。

## R-02 为什么不是「全部 404 化」

**备选**：把所有 403 都改成 404，最"一致"。

**为什么不行**：403 有两种完全不同的语义，混改会把「知道自己有资源、但缺一个
字段权限」的场景变成「资源不存在」，用户会误以为数据丢了。典型例子：
- assignee 改 `project_id` → 403（他经手这个需求，只是不能挪项目）
- 项目成员管理成员 → 403（他能看到项目，只是不是 owner）
- viewer 写端点 → 403（角色不足，与任何资源无关）

**结论**：判据是「访问者是否已被告知/已知该资源存在」。已参与者 → 403；
非参与者 → 404。见 contracts 的错误码矩阵。

## R-03 为什么 message 也要统一，不能只改状态码

如果 404 的 message 写成「无权访问该需求」，那么不暴露存在性的目的就落空了——
message 直接说了「它存在」。所以 message 必须是**中性的存在性描述**
（「需求不存在」「Agent 不存在」），与真正不存在的响应逐字一致。

这也是 SC-003 要断言「两次响应体相等」的原因：只断言状态码相等，会漏掉 message 泄露。

## R-04 为什么不动 admin 的越权读

`GET /schedules` 里 admin 能读他人规则、但不能改，那里 403 是**正确的**：
admin 本来就能看到全部，403 不携带任何「存在性」增量信息。

同理 `schedule_service` 的注释（「读路径对他人一律 404，但 admin 本来就能读到任何调度，
403 不携带信息」）已经把这个推理写清楚了，本特性只是把它推广到全站。

## R-05 改哪些、不改哪些：判定流程

```
请求 → 资源是否存在？
  ├─ 否 → 404（既有行为）
  └─ 是 → 访问者与该资源有关系吗？
        ├─ 否 → 404（本特性要改的）
        └─ 是 → 缺的是角色还是字段权限？
              ├─ 角色（viewer）→ 403
              └─ 字段/动作（非 owner 做 owner 动作）→ 403
```

「有关系」的定义按资源：
- 需求：创建者 ∪ 接收人 ∪ 项目成员
- Agent / 组 / 出网规则 / 外部工具：owner
- 内置模板：全体可见（`owner_id IS NULL`）

## R-06 为什么测试要新增「响应体相等」断言

既有测试大量断言 `status_code == 403`，改状态码时把它们改成 404 只是"让测试变绿"，
并不能防止有人下次把 message 改成泄露版本。

新增用例的做法：对同一个资源，分别用「不存在的 id」和「他人拥有的 id」发请求，
断言 `response.json() == missing_response.json()`。这样 message 一泄露就会红。

## R-07 迁移成本：为什么这次能做（而 007 时期不能）

007 时期不做，是因为当时 001 的契约刚锁定、`test_requests.py` 里有大量断言，
在业务特性里顺手改错误码会让「需求分派」这个 PR 的 diff 里混进 50+ 行无关改动，
review 无法判断哪个改动是有意的。

现在单独一个特性、单独一个分支，diff 里**只有**错误码相关的改动，
reviewer 可以逐条确认「这处该 404、那处该留 403」。
