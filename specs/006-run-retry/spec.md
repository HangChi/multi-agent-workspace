# Feature 006: 运行自动重试（Run Auto-Retry）

> **Branch**: `feat/006-run-retry` | **Date**: 2026-11-18 | **Spec**: [spec.md](spec.md)
>
> 关联：[001-core-workflow](../001-core-workflow/spec.md)（FR-017 手动重试的扩展）、
> [005-agent-templates](../005-agent-templates/spec.md)（同仓库的上一特性，工作流参照）。

## 1. 背景与问题

今天一个 Run 执行失败后**只有一条路**：用户自己点「重试」。这带来三个具体问题：

1. **瞬时失败要人等。** LLM 网关抖动、连接重置、Worker 与网关之间的瞬时网络问题，
   都会让一个本来会成功的任务停在 `failed`。用户必须盯着看板，手动点重试。
2. **`max_retries=2` 是死代码。** `execute_run` 任务声明了 Celery 的 `max_retries=2`，
   但代码里没有任何 `self.retry()` 调用；所有异常被 catch 后标记失败并正常返回，
   Celery 认为任务「执行成功」，永远不会触发自己的重试。这个参数有误导性。
3. **重试不要重复执行、也不要免费。** 一旦引入自动重试，两个风险立刻出现：
   同一次执行被触发两遍（重复花 token、重复写制品），以及重试的成本不计入配额与熔断。

## 2. 目标与非目标

### 2.1 目标（In Scope）

- 对**瞬时类失败**自动重试，用户无需干预；等待期间进度可见。
- 重试**不得重复执行**：任何时刻同一个 Run 只有一个执行体在跑。
- 成本**跨重试累计**：重试花的 token 照记，成本上限按累计值判断。
- 重试过程可观测：第几次、上次为什么失败、下次什么时候开始，都能查到。
- 与既有手动重试统一口径：手动重试同样累计成本（原为重置）。

### 2.2 非目标（Out of Scope，显式不含）

- **不重试业务类失败**：配额超限、成本超限、步数超限、用户取消、Agent 被删、
  组内无可用成员、pipeline 某阶段业务失败。这些重试一次还是同样的结果。
- **不做死信队列（DLQ）**：重试耗尽即终态 `failed`，由用户决定是否手动重来。
- **不改 pipeline / fan_out 的父子失败语义**：子 Run 各自独立重试，
  父 Run 的收敛规则不变（本特性只改单个 Run 的生命周期）。
- **不做跨 Worker 的重试协调**：重试调度依赖既有 Redis 锁，不引入分布式协调组件。
- **不改 reaper 的阈值语义**：只保证 reaper 不误杀正在等待重试的 Run。

## 3. 用户故事与验收标准

### US1 — 瞬时失败自动恢复（优先级 P1）

运维把 LLM 网关重启了 3 秒。这期间被分配的一个任务第一次调用失败。
**期望**：系统自动重试，用户看到「第 2/3 次 · 4s 后重试」，任务最终完成，
用户没有做任何操作。

**验收场景**：

- **Given** 一个 Run 正在执行且第 1 次因网关连接失败而中断，
  **When** 系统判定该失败为瞬时类，
  **Then** Run 进入重试等待，界面显示当前是第几次尝试与距下次尝试的秒数。
- **Given** 重试等待中，**When** 到达预定时刻，
  **Then** 系统重新开始执行，且用户无需任何操作。
- **Given** 一个 Run 已自动重试成功，**When** 用户查看运行详情，
  **Then** 能看到它重试过、以及每一次失败的原因。

### US2 — 重试不重复执行（优先级 P1，安全相关）

用户在重试等待期间手动点了「重试」，同时定时重试也到点触发。
**期望**：这个 Run 只被执行一次，不会出现两份制品、双倍扣费。

**验收场景**：

- **Given** 一个 Run 正在执行中，**When** 同一 Run 的另一次执行被触发
  （定时到点、手动重试、消息重投），
  **Then** 后到的那次被拒绝，不产生第二次执行、不产生额外成本。
- **Given** 一个 Run 已进入终态 `completed`，**When** 延迟的重试消息到点，
  **Then** 该消息被丢弃，不产生任何状态变化与成本。

### US3 — 成本跨重试累计（优先级 P1，计费相关）

一个任务第 1 次执行花了 30 分后失败，重试又花了 25 分后成功。
**期望**：这个 Run 记录的成本是 55 分，而不是 25 分；如果累计超过成本上限，
在执行过程中就被熔断，而不是「每次尝试各自算、永远熔不断」。

**验收场景**：

- **Given** 一个 Run 第 1 次尝试已产生成本后失败，**When** 它进入重试，
  **Then** 已发生的成本被保留，不清零。
- **Given** 一个 Run 的累计成本（含历次尝试）已达到成本上限，
  **When** 重试尝试继续执行，**Then** 执行被熔断并标记失败，不会超支。
- **Given** 用户对一个已失败的 Run 手动重试，**When** 重试执行完成，
  **Then** 成本同样跨次累计（与自动重试口径一致）。

### US4 — 重试过程可观测（优先级 P2）

一个任务重试 2 次都失败了。用户和运维需要知道：它试过几次、每次败在什么地方、
是不是网关的问题。

**验收场景**：

- **Given** 一个 Run 重试耗尽后失败，**When** 用户查看运行详情，
  **Then** 能看到尝试次数与每一次的失败原因。
- **Given** 一个 Run 正在重试等待，**When** 看板刷新，
  **Then** 该卡片显示为重试中，且不与「执行中」「失败」混淆。

## 4. 功能需求

### 失败分类

- **FR-001**: 系统 MUST 将执行失败分为「瞬时类」与「业务类」两类。
- **FR-002**: 系统 MUST 仅对瞬时类失败自动重试；业务类失败 MUST 直接终态，
  不得自动重试。
- **FR-003**: 瞬时类 MUST 至少包括：LLM 网关连接失败、LLM 网关超时、
  网关返回 5xx、工具调用因网络原因失败。
- **FR-004**: 业务类 MUST 至少包括：配额超限、成本超限、步数超限、执行超时、
  用户取消、Agent 或上下文缺失、组内无可用成员、工具被策略拒绝。
- **FR-005**: 无法归类为瞬时类的未知异常 MUST 按业务类处理（重试保守原则）。

### 重试调度

- **FR-006**: 系统 MUST 支持自动重试，重试次数上限 MUST 可配置，默认
  「首次执行 + 2 次重试」共 3 次尝试。
- **FR-007**: 重试间隔 MUST 采用指数退避：以上一次等待时长为基准翻倍，
  首次等待基准可配置；实际等待时长 MUST 加入随机抖动（jitter）以避免
  多个失败任务同时重试造成二次冲击。
- **FR-008**: 退避等待时长 MUST 有上限（可配置，默认 60 秒），避免长尾等待。
- **FR-009**: 重试次数耗尽后，Run MUST 进入终态 `failed`，并保留最后一次
  失败原因与全部历史失败原因。

### 不重复执行

- **FR-010**: 任何时刻，同一个 Run MUST 至多有一个执行体在运行。
- **FR-011**: 重试到点触发时，系统 MUST 校验 Run 仍处于可执行状态
  （未被取消、未被删除、未已终态）；不满足则丢弃本次触发。
- **FR-012**: 重试等待期间，僵尸回收机制 MUST NOT 将该 Run 判为卡死。

### 成本

- **FR-013**: 成本 MUST 跨重试尝试累计，手动重试与自动重试口径一致。
- **FR-014**: 成本熔断 MUST 按累计成本（含历次尝试）判断，不得因重试重置而绕过。
- **FR-015**: 用户 MUST 能在运行详情看到本次运行的累计成本，以及（若有）重试次数。

### 状态与可观测

- **FR-016**: 系统 MUST 为「重试等待中」提供独立的状态标识，使用户能区分
  「正在执行」「正在等待重试」「已失败」。
- **FR-017**: 重试的每次尝试（第几次、失败原因、耗时）MUST 可查询。
- **FR-018**: 自动重试的发生与结果 MUST 写入审计日志。
- **FR-019**: 重试等待开始与重试执行开始 MUST 推送实时事件给前端。

### 兼容性

- **FR-020**: 手动重试端点的外部契约（路径、状态码、响应体）MUST 保持不变。
- **FR-021**: 本特性 MUST NOT 改变 pipeline / fan_out 父子 Run 的收敛规则。

## 5. 成功标准

- **SC-001**: 瞬时失败（网关连接中断）场景下，任务在无人干预的情况下完成，
  全程 ≤ 3 次尝试（含首次）。
- **SC-002**: 并发触发同一 Run 的多次执行（定时到点 + 手动重试）时，
  实际执行次数为 1，成本记录无重复。
- **SC-003**: 跨 2 次尝试的成本累计值等于两次尝试各自成本之和；
  累计达到上限时第 3 次尝试被熔断。
- **SC-004**: 重试等待期间看板不出现「卡死」，僵尸回收不误判。
- **SC-005**: 重试耗尽失败的 Run，详情页可读出全部尝试次数与每次失败原因。
- **SC-006**: 既有手动重试的集成测试除成本口径外全部保持通过（契约不破）。

## 6. 范围边界（防膨胀）

明确**不做**：

1. 死信队列、重试策略按错误类型分别可配（统一一套策略，仅上限/基准/封顶可配）。
2. 重试进度条动画、重试历史的时间线视图（本期只做文字与计数）。
3. 跨进程的重试协调服务、重试元数据的外置存储。
4. 对 pipeline 父 Run 的自动重试（父 Run 仍按现有收敛规则走）。
5. 退避策略的「装饰性抖动」可视化（jitter 只影响调度，不展示计算过程）。

## 7. 关键实体

| 实体 | 说明 |
|---|---|
| Run | 既有执行实体；本特性为其增加「尝试次数」「下次重试时刻」「历次失败原因」 |
| 尝试（Attempt） | 一次实际的执行；一个 Run 有 1..N 次尝试，N 受上限约束 |
| 失败分类 | 瞬时类 / 业务类的判定结果，决定是否自动重试 |

## 8. 假设（Assumptions）

1. **默认 3 次尝试**：首次 + 2 次重试。依据：主流 SDK（AWS、Stripe、OpenAI）
   的默认重试次数在 2–3 次量级；且每次尝试都在花真实 token，次数越高成本风险越大。
2. **退避基准 2 秒、封顶 60 秒**：2s → 4s 两跳总等待约 6 秒，用户几乎无感；
   封顶值远大于任何合理的瞬时故障恢复时间。
3. **full jitter**：等待时长在 `[0, 计算值]` 区间随机取，而非固定值。
   依据：AWS《Exponential Backoff and Jitter》给出的方案，用于避免惊群。
4. **成本累计而非重置**：看板数字必须对得上真实支出；重置会让配额统计系统性偏低。
5. **重试状态独立于终态**：重试等待是一个中间态，失败仍是终态，
   两者在界面上必须可区分（否则用户以为任务已失败并重复手动操作）。
6. **幂等由既有 Redis 锁承担**：锁的 TTL 已覆盖单次执行时长，本特性复用而不新建。
