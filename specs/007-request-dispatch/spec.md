# Feature 007: 需求分派给员工与收件箱（Request Dispatch & Inbox）

**Feature Branch**: `feat/007-request-dispatch`
**Created**: 2026-11-18
**Status**: Draft
**Input**: 设计动机对齐审计结论（2026-11-18）——系统当前只支持「谁建需求谁拖给 Agent」，缺「需求 → 员工」一跳；本特性补齐公司内部系统的核心闭环。

## 1. 背景与问题

系统的原始设计动机是**公司内部系统**：每个员工可以接收到对应的需求，然后员工将需求拖拽到
对应的 Agent 来处理。但 001–006 六个特性落地后，实际形态是「个人/小团队把自己的需求拖给
Agent 执行的编排工具」：

- 需求卡片只有创建者（owner），**没有接收人概念**——需求无法「到」员工手里；
- 拖拽落点只有 Agent 与 Agent 组，**人不能作为落点**；
- 需求列表按创建者隔离，每个人看到的是自己的草稿板，**没有团队需求池/收件箱**。

后果：大型项目中「谁负责哪件事」只能靠线下沟通，系统不感知；需求分派、认领、退回、转交
全部在系统外发生，看板上的状态反映不了真实的责任分配。

**本特性不做执行引擎的改动**（ReAct、编排策略、成本熔断、实时推送全部原样保留），只补
「需求 → 员工 → Agent」中缺失的第一跳，并让员工对「分派给自己的需求」拥有合法的操作权。

## 2. 目标与非目标

### 2.1 目标（In Scope）

1. **需求分派给员工**：需求卡片可以拖到员工卡片上（或经人员选择器指定），需求进入
   `pending`（待接收）状态，接收人的收件箱立即可见，并产生一条未读通知。
2. **员工接收/退回/转交**：接收人可 `accept`（进入 `accepted`，待其处理）、可 `reject`
   退回（附原因，需求回到创建者手里）、可分派方/创建者/接收人一方转交给另一位员工。
3. **员工执行分派来的需求**：`accepted`（或创建者本人）可将需求拖给 Agent/组，走既有
   分配与执行链路；执行成本与月配额记在**需求创建者**名下（见 FR-009）。
4. **收件箱与「与我相关」视图**：需求列表支持「分派给我的」（收件箱）与「我创建的」两种
   范围；看板出现「待接收」列。
5. **站内通知**：分派、接收、退回、转交、执行完成均产生站内通知，顶栏有未读标识与通知
   中心（列表 + 一键已读）。
6. **人员选择**：提供最小化的在职用户列表供分派选人。
7. **全程留证**：分派/接收/退回/转交全部写入审计日志与分派历史（谁在什么时候把需求给了谁、
   为什么退回）。

### 2.2 非目标（Out of Scope，显式不含）

| 项 | 依据 |
|---|---|
| Project 实体、需求归属项目、项目看板 | 留 008；本特性只补「需求→员工」一跳，项目容器是独立的领域概念 |
| 需求之间的依赖与编排（A 完成触发 B） | 留 008；与分派解耦，避免单特性过大 |
| 邮件 / Webhook / 企业微信通知 | 本期只做站内通知（宪法：生产化要素分阶段落地，外部通道涉及凭证与投递可靠性，需独立特性论证） |
| 组织架构（部门、上下级、汇报线）与分派权限矩阵 | 无组织数据模型；本期任何在职员工均可被分派、均可转交，权限收敛留组织维度引入时 |
| 自动分派规则引擎（按关键词/负载自动选人） | 定时调度（004）已覆盖「系统自动建单」，本期只补「人到人」的手动分派；规则引擎需要负载数据支撑，留后续 |
| 管理员全量需求视图 | 属管理后台范畴，与 003 审计日志同路，留后续 |
| 需求认领池（多人抢单） | 与「指定接收人」是两种分派模型，混用会让 pending 语义歧义；留后续评估 |

## 3. 用户故事与验收标准

> 每个故事独立可测：只实现 US1–US3 即构成最小可用闭环（能分派、能接收、能执行）。

### US1 — 把需求分派给员工（优先级 P1）

作为需求创建者或当前经手人，我希望把需求卡片拖到某位员工卡片上（或在分派弹窗里选择员工），
让需求进入对方的收件箱，而不必再口头告知。

**验收标准**：

- **Given** 我有一条非终态、不在执行中的需求，看板上展示着在职员工卡片
  **When** 我把需求卡片拖到员工卡片上并确认
  **Then** 需求状态变为「待接收」，该员工出现在需求详情的分派信息里，对方收件箱出现该需求
  **And** 对方收到一条未读通知，内容含需求标题与分派人
- **Given** 一条已在我手里（我创建的或分派给我且已接收）的需求
  **When** 我把它拖给另一位员工
  **Then** 原经手链记录一条转交历史，新接收人收到通知，旧接收人（若非我本人）收到转交通知

### US2 — 员工接收、退回与转交（优先级 P1）

作为接收人，我希望明确接收分派给我的需求；不合适时能附原因退回，也能转交给更合适的同事。

**验收标准**：

- **Given** 一条分派给我、处于「待接收」的需求
  **When** 我点「接收」
  **Then** 需求变为「已接收」，分派人收到「已接收」通知，我成为该需求的当前经手人
- **Given** 一条分派给我、处于「待接收」或「已接收」的需求
  **When** 我点「退回」并填写原因
  **Then** 需求回到「待处理」（创建者手里），分派信息清空，分派人收到含退回原因的通知，
  历史里留下「谁、何时、为什么退回」
- **Given** 一条分派给我、处于「待接收」或「已接收」的需求
  **When** 我把它转交给另一位员工
  **Then** 需求变为「待接收」且接收人变为新同事，新同事收到通知，历史记录一条转交

### US3 — 员工把分派来的需求拖给 Agent（优先级 P1）

作为接收人，我希望把接收到的需求拖到 Agent 或 Agent 组上启动执行，就像处理自己的需求一样。

**验收标准**：

- **Given** 一条我已接收（或我创建）的需求
  **When** 我把它拖到 Agent/组上并选择策略
  **Then** 与现状完全一致地创建 Run、入队执行、实时可见，产出与制品归属该需求
- **Given** 一条别人分派给我、我已接收的需求
  **When** 我完成一次执行
  **Then** 本次执行的 token 成本计入**需求创建者**的月配额与成本统计，不计入我的配额
  **And** 创建者收到「执行完成」通知
- **Given** 一条分派给我但**尚未接收**的需求
  **When** 我尝试把它拖给 Agent
  **Then** 被拒绝（需先接收），需求状态不变

### US4 — 收件箱与「与我相关」列表（优先级 P1）

作为员工，我希望打开看板就看到「分派给我的」和「我创建的」两类需求，不漏掉派给我的活。

**验收标准**：

- **Given** 我已登录且有分派来的需求
  **When** 我看板选择「收件箱」范围（或默认的相关视图）
  **Then** 列表包含分派给我的全部需求（含待接收/已接收/以及我经手后进入执行及以后状态的），
  不含只属于别人的需求
- **Given** 我看板选择「我创建的」范围
  **Then** 行为与现状完全一致（向后兼容）
- **Given** 一条分派给我、处于「待接收」的需求
  **WHEN** 顶栏未读铃铛显示数字
  **THEN** 该需求对应 1 条未读；我接收或读掉通知后数字减 1

### US5 — 站内通知中心（优先级 P2）

作为员工，我希望有一个地方回顾「谁给我派了活、谁退回了我的需求、我派出的需求到哪了」。

**验收标准**：

- **Given** 我过分派/接收/退回/转交/有分派需求执行完成的事件发生
  **When** 我打开通知中心
  **Then** 每条通知显示类型、相关需求标题、时间；未读有标识
- **Given** 通知中心有未读
  **When** 我点「全部已读」（或逐条点开）
  **Then** 未读计数归零，顶栏铃铛标识消失

### US6 — 分派链路的边界与安全（优先级 P1，边界故事独立）

分派引入新的状态与新的操作者，边界行为必须与既有归属纪律一致，且不能破坏现有链路。

**验收标准**：

- **Given** 一条已在执行中（已拖给 Agent）或已终态的需求
  **When** 任何人尝试分派/接收/退回/转交
  **Then** 被拒绝并提示「需求已在执行/已终结」，状态与分派信息不变
- **Given** 一条分派给员工 A 的需求
  **When** 员工 B（非创建者、非当前接收人）尝试查看详情、接收、退回、转交或拖给 Agent
  **Then** 与现状一致的「不存在」响应（不暴露需求存在性），且不产生任何状态变化
- **Given** 接收人账号被禁用（离职）
  **When** 其收件箱中的需求仍处于待接收
  **Then** 创建者/经手人可将需求转交给其他在职员工；被禁用用户不出现在人员选择列表中
- **Given** 一条需求
  **When** 创建者把需求分派给自己
  **Then** 允许（单人闭环：自派自接），行为与分派他人一致
- **Given** 一条已处于「待接收」的需求
  **When** 有人再次把它拖给另一位员工
  **Then** 按转交处理（不是报错），历史记录两条：首次分派、本次转交
- **Given** 一条待接收的需求，创建人与接收人**同时**点接收/退回
  **When** 两个请求到达服务端
  **Then** 只有一个成功，另一个收到冲突提示，最终状态与胜出一致，历史只有一条对应记录

## 4. 功能需求

### 分派与状态

- FR-001：系统 MUST 支持把需求分派给一名在职员工；分派后需求进入「待接收」状态并记录接收人。
- FR-002：需求状态机 MUST 扩展为：`待处理 → 待接收 → 已接收 → 已分配 → 执行中 → 已完成`，
  另有 `失败/已取消` 终态与既有重试中间态；所有迁移 MUST 集中校验，非法迁移被拒绝。
- FR-003：退回 MUST 将需求回到「待处理」（创建者手里）并清空接收人；退回 MUST 可带原因，
  原因必填（一句话说清为什么退）。
- FR-004：转交 MUST 更换接收人并保持「待接收」状态；首次分派与转交走同一条记录通道，
  历史中 MUST 可区分。
- FR-005：分派/接收/退回/转交对「执行中及以后状态」的需求 MUST 一律拒绝（409），状态不变。
- FR-006：自派（创建者分派给自己）MUST 允许，且接收后创建者即经手人。

### 可见性与操作权

- FR-007：需求列表 MUST 支持两种范围：「与我相关」（我创建的 + 分派给我的，默认）与
  「我创建的」（与现状一致）；终态需求也按同一范围可见。
- FR-008：需求详情与分派操作的访问权 MUST 为「创建者或当前接收人」；其他人 MUST 得到与
  「不存在」一致的响应（延续既有归属纪律，不暴露存在性）。
- FR-009：执行成本与月配额 MUST 记在需求创建者名下（与 Run 既有归属继承一致），
  不因经手人变化而改记。

### 通知与人员

- FR-010：分派、接收、退回、转交、执行完成 MUST 各产生一条站内通知给对应方
  （分派人/创建者/接收人/旧接收人）。
- FR-011： MUST 有未读计数，读完后计数减少；通知 MUST 可按时间倒序回溯。
- FR-012：人员选择 MUST 只暴露在职用户的最小信息（身份标识与显示名），禁用账号 MUST 不在列。
- FR-013：分派、接收、退回、转交 MUST 全部写入审计日志（操作人、对象、结果）。

### 兼容

- FR-014：现有「拖给自己的需求 → Agent」链路 MUST 零变化（同库同接口同行为）。
- FR-015：定时调度（004）自动建单产生的需求 MUST 继续归属创建规则的人，可被正常分派。

## 5. 成功标准

- SC-001：分派操作从拖拽确认到对方收件箱可见，端到端 P95 < 5 秒（含 WS/轮询刷新），
  服务端受理 P95 < 100ms（对齐宪法 API 层纪律）。
- SC-002：US6 全部边界场景有集成测试覆盖且通过；每条边界测试直接对应 FR-005/008/012。
- SC-003：分派、接收、退回、转交、通知已读五类操作审计覆盖率 100%（有操作必有审计行）。
- SC-004：并发接收/退回同一需求，仅一个成功，终态确定，历史不重复（集成测试用两个并发请求断言）。
- SC-005：员工执行分派需求后，创建者月配额消耗增加、执行人配额不变（集成测试断言两边配额数）。
- SC-006：收件箱范围与「我创建的」范围在同一数据量下响应时间不回退（集成测试计时断言上限）。
- SC-007：前端拖拽到员工卡有明确落点视觉与确认弹窗；未读铃铛在通知产生后无需手动刷新页面
  在 30 秒内反映（轮询或推送任一，验收以真实浏览器或等价端到端脚本为准）。

## 6. 范围边界（防膨胀）

1. 不做项目容器与需求依赖（008）。
2. 不做外部通知通道与规则引擎（见 §2.2）。
3. 不改执行引擎、编排策略、成本熔断、Run 状态机（006 刚定稿，不动）。
4. 不做认领池/抢单。
5. 管理后台的全量分派视图不做（可用现有审计日志排查）。
6. 分派弹窗不提供「批量分派多条需求」（单条操作，批量留后续按需）。

## 7. 关键实体

- **需求（Request）**：新增「接收人」「分派时间」「接收时间」属性；状态枚举扩展
  「待接收」「已接收」。
- **分派历史（Dispatch Record）**：一条需求每次「分派/转交/接收/退回」产生一条不可变记录：
  动作、操作人、原接收人、新接收人、原因、时间。
- **通知（Notification）**：发给某用户的站内消息：类型、关联需求、已读时间。
- **在职用户（User）**：既有实体；新增最小化列表查询能力，无结构变化。

## 8. 假设（Assumptions）

1. 「员工」即系统注册用户（三角色不变）；分派不感知部门与上下级（无组织数据）。
2. 默认看板范围改为「与我相关」是可接受的产品变化——它严格扩大可见范围（自己的 + 派给我的），
   不缩小任何人现有可见集。
3. 成本与配额记创建者：与 Run 既有归属继承（`Run.owner_id = Request.owner_id`）同源，
   本特性不引入第二套归属口径。
4. 通知的实时性用「轮询未读数（≤30s）」或「WS 推送」实现均在验收标准内，选型在 plan 阶段定，
   以不增加长连接复杂度为目标。
5. 分派原因/退回原因按纯文本存储，长度上限与需求描述一致量级（≤2000 字符）。
6. 现有集成测试中「只能分配自己的需求」的断言，在本特性中按 FR-008 收窄为「创建者或接收人」，
   属有意的契约变更，将在 tasks 中逐条更新并说明。
