# Feature Specification: 邀请码运营（022）

**Status**: Partially implemented（2026-11-21）

**Input**: 用户 2026-11-21「A1–A6 逐个完成」中的 A6：用量统计 / 批量发码 /
部门限额 / 申请-审批流。

## 现状盘点（先看清楚什么已经有了）

015 只做了「发放 / 列表 / 吊销」三件事，另外**批量发码在 015 就已经做了**
（`POST /admin/invite-codes/batch`，1..20 张）。所以 A6 的真实缺口是三项：

| 子项 | 状态 |
|---|---|
| 批量发码 | ✅ 015 已有，022 只补部门归属 |
| 用量统计 | 🆕 022（`GET /admin/invite-codes/stats`） |
| 部门限额 | 🆕 022（`departments.invite_quota` + 发码时校验） |
| 申请-审批流 | ❌ **未做**（见「未做与理由」） |

## 问题陈述

「谁能进系统」由邀请码控制（015 的判断），但运营层面缺三样东西：

1. **招人进度看不见**：发了多少名额、用了多少、哪个码在用——只能一个个数列表；
2. **招人预算没有归属**：公司按部门给 HC，而码不带部门，配额只能全局拍一个数，
   于是先招的部门把额度吃光；
3. （未做）**发放要走审批**：非 admin 想加人只能找管理员口头说。

## 设计

### 1. 部门归属 + 月度名额配额

- `departments.invite_quota`（可空 = 不限）：该部门**每月**可通过邀请码新增的
  名额上限。发码时校验「本月已发 `SUM(max_uses)` + 本次 ≤ quota」。
- `invite_codes.department_id`（FK `SET NULL`）。
- **撤销不释放名额**：发出去就占用预算，否则「发了再撤销」能绕过上限。
  配额是预算，撤销是「这张码还能不能用」，两个概念。
- **批量整批校验**：`count × max_uses` 一次性校验。逐张校验会在中途超限，
  留下半批码（哪几张生成了？怎么回收？都难解释）。

### 2. 统计总览

`GET /admin/invite-codes/stats`：

```json
{"total_codes": 12, "issued_seats": 120, "used_seats": 87,
 "by_role": [{"role": "member", "codes": 10, "issued_seats": 100, "used_seats": 80}],
 "by_department": [{"department_id": "...", "department_name": "平台组",
                    "quota": 20, "issued_seats_this_month": 12,
                    "used_seats_this_month": 9}],
 "top_codes": [{"code": "AW-XXXX", "role": "member", "max_uses": 5, "used_count": 5}]}
```

两个口径分开：**已发名额**（`SUM(max_uses)`）与**已用名额**（`SUM(used_count)`）。
合成一个数会导致「发了 100 个用 3 个」和「发 3 个用 3 个」看起来一样。

## 需求

- **FR-001** `departments.invite_quota`（int，可空）+ `invite_codes.department_id`
  （FK SET NULL）+ 索引。
- **FR-002** 单张/批量发码接受 `department_id`；部门不存在 404。
- **FR-003** 部门有配额时，本月已发名额 + 本次 > 配额 → **409**，消息带「已发 / 上限」。
- **FR-004** 批量整批校验（不留半批）。
- **FR-005** 统计端点：总量 / 按角色 / 按部门（含本月与配额）/ 使用最多的 5 个码。
- **FR-006** 统计与发码均 admin-only。
- **FR-007** 列表与单张返回带 `department_id` + `department_name`。
- **FR-008** 前端：管理后台邀请码区显示运营概览（三个 KPI + 按部门本月进度），
  发码表单可选部门。

## 成功标准

- SC-001 配额 3、发 max_uses=2 → 201；再发 2 → 409。
- SC-002 批量 3×2 超过剩余 5 → 409 且**一张码都没落库**。
- SC-003 撤销后不释放名额（再发仍 409）。
- SC-004 无配额部门不受限。
- SC-005 统计的 issued/used 口径正确，by_department 只统计**本月**发出的码。

## 未做与理由（如实记录）

**申请-审批流**（member 提交「我要 2 个名额给某人」→ admin 审批 → 自动发码）没有实现：

1. 它是一条**新的业务流程**（申请表、状态机、审批通知、超时处理、前端两个页面），
   体量与 018 相当，不是「邀请码页加个按钮」；
2. 它与 022 已做的「部门配额」正交：没有审批流，配额仍然限制得住预算；
   有了配额，审批流的价值主要变成「留痕」——而审计表已经在记发码动作；
3. 真要做，正确形态是「配合组织架构的 HC 管理」（部门编制、在职人数、离职释放），
   那是 023 级别的东西。硬塞进 022 只会做出一个「能点但没人用」的表单。

**没有实现的部分不勾选，也不假装它存在。**
