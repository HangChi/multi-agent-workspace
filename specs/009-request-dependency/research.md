# Research: 009 需求依赖编排

编号 `R-01…`。每条写**决策 / 依据（带实测或既有契约）/ 被否决的方案及理由**。

## R-01：门禁判据是「前置是否终态」，不是「是否成功」

- **决策**：`completed / failed / cancelled / timeout` 都解锁；只有这四种之外的状态（created/pending/accepted/assigned/running）挡路。
- **依据**：门禁的语义是**顺序**（「别在 A 结束前启动 B」），不是成败传播。若只有 completed 解锁，failed 的前置会把后续方永久挡死，用户必须去做「边外科手术」（删边）才能继续——一个失败的 A 不应该让 B 永远无法启动，B 的前提是否被破坏是人的判断，不是系统的。
- **被否决**：仅 completed 解锁。理由如上（死锁 + 逼用户删边）。以及「failed 的前置自动取消后续方」——系统替人做「这事不用干了」的决定，不可逆且无确认点。

## R-02：解锁通知落在 settle_request_status，不落在 execute_run 的各完成分支

- **决策**：通知在 `settle_request_status`（需求状态收敛函数）内、设置终态后发出。
- **依据**：settle 是需求到达终态的**唯一汇聚点**（完成/失败/取消/超时都经过它，execute_run 的注释明说「放在 finally 里，失败/取消/超时同样收口」），且它的 `status != "running"` 早退**免费保证了幂等**——需求离开 running 后再也不会收敛第二次。落在 execute_run 的各分支要重复四次同样的逻辑，且取消路径（runs.py）不走 execute_run，会漏。
- **被否决**：在每个 Run 终态分支各发一次。理由：四处置错风险 + 取消路径遗漏 + 幂等要自己实现（settle 的白拿）。

## R-03：不加 blocked 状态，门禁是分配时的前置校验

- **决策**：需求状态机保持 8 态；「被挡住」不是状态，是 assign 时的一次校验失败。
- **依据**：用户范围确认时明确「硬门禁 + 完成通知」，未提状态；加 blocked 态的代价是状态机 +2 态迁移、看板 +1 列、007/008 的全部状态断言要回归，而收益只是「看板多一列」——同样的信息用卡片徽章（US4）零状态成本给出。
- **被否决**：blocked 态。理由：状态膨胀与回归面，且 blocked→created/accepted 的迁移规则（前置终态后谁把它推回去？settle 只推 running 的需求）要把收敛逻辑扩展到全状态——那是把「查询」做成「状态机」的典型过度设计。

## R-04：成环检测用 BFS，不用递归 CTE

- **决策**：加边时在 service 内从 `dependency_id` 沿既有边 BFS，若能到达 `request_id` 则拒绝。
- **依据**：实测当前 21 条需求 / 5 用户；即使到几百条需求，单需求的依赖子图也是个小图，BFS 的代价是「一次按 request_id 取边 + 内存遍历」。递归 CTE 要把图遍历下推给 PG，SQL 复杂且执行计划随深度不可控，而这里的深度上限就是需求数——没有大数据场景需要它。
- **被否决**：PG 递归 CTE（`WITH RECURSIVE`）。理由：为理论上才需要的规模牺牲可读性；且 CTE 版本无法在单测里用 SQLite 跑（项目测试库是真实 PG，但单元测试层面 BFS 可纯函数测）。

## R-05：依赖目标不做可见性校验（内部协作工具的取舍）

- **决策**：`dependency_id` 可以是任何用户创建的需求；不要求操作者对目标有读权限。
- **依据**：这个特性最自然的用法是「B 等隔壁团队的 A」——要求连边者看得见 A，等于把跨人协作（特性的核心场景）挡死。内部工具里需求标题不是敏感资产（对比：凭证/密钥才有 404 纪律）。
- **被否决**：要求目标可见（owner-or-assignee）。理由：挡住核心场景。残余风险（连边者可借 404/201 探测他人需求存在性）记录在此：内部工具 + 需要先拥有某条需求的编辑权才能尝试连边，探测面已很小；若将来出现真实泄露事件，再加「目标须与我在同一项目或同一分派链」的约束。
- **展示侧配套**：边列表与 409 消息直接展示目标标题（不再做 visible 标记）——同一权衡的展示侧，做了可见性校验却又展示标题是自相矛盾。

## R-06：边的管理权 = 被依赖方的 owner-or-assignee

- **决策**：增/删边要求对 `request_id` 侧需求有编辑权（与标题/描述同谓词）。
- **依据**：经手人是撞门禁的人——他被 409 挡住时，最常见正确的动作就是删掉那条误连的边；要求他回去找创建者是一趟无效往返。不同于 008 的 `project_id` 仅创建者可改：那是**可见性字段**（经手人挪项目会让创建者视图静默丢活），边不是可见性字段（删边不隐藏任何东西，且审计留痕）。
- **被否决**：仅创建者可改（与 project_id 一致）。理由：把「改结构」与「改归属」混为一谈；边的增删影响的是执行门禁，经手人是直接利益相关方。

## R-07：定时调度撞门禁 = 建单不分配，不记 failed

- **决策**：`_fire_and_assign` 在调 assign 前先查门禁；未满足则跳过分配，trigger 记 `result=fired` + `reason="前置未完成，未自动分配"`，需求留在 created。
- **依据**：实测 004 的 `_fire_and_assign` 对 assign 抛出的 AppError 是「rollback 整个事务 → 记 failed」——那条路径**连需求一起回滚**（注释明说防止「用户只看到什么都没发生」）。若门禁错误走这条路，定时规则每撞一次门禁就丢一条需求，且触发历史记 failed 会累积连续失败计数、最终 auto-disable 规则——一个完全正常的「前置还没好」会把调度规则自动停掉。
- **被否决**：让门禁错误走既有 failed 路径。理由如上（丢需求 + 误停规则）。以及「调度规则对带依赖的需求直接不建单」——丢需求且用户看不到「规则到过点」。

## R-08：重试不重查依赖

- **决策**：006 的重试路径不查门禁。
- **依据**：门禁保证「running 的需求没有未完成前置」，所以重试（只在 failed 后发生）时前置必然已终态——重查是纯浪费一次往返，还会引入「重试间隙前置被删/被改」的奇异状态（跑还是不跑？）。
- **被否决**：重试前重查。理由：浪费 + 奇异状态；且违反「门禁只在启动时判定一次」的心智模型。
