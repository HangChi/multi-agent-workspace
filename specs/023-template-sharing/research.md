# Research：模板共享 / 版本历史 / 导入导出（023）

## R-01 为什么快照而不是 diff

模板是 9 个标量字段 + 名字 + 描述，一份快照 JSON 约 1~2KB。存 diff 的收益是省空间，
代价是**回滚要按序重放**：任一版本缺失或顺序错乱，还原出来的就是一个「半新半旧」
的配置，而且不会有任何报错——这种静默错误比多存几 KB 危险得多。

保留 20 个的上界让存储成本变得无关紧要（20 × 2KB = 40KB/模板）。

## R-02 为什么回滚也要记一条历史

「回滚到 v3」本身是一次修改。如果不记，用户回滚后发现还是不对，想「回到回滚前的状态」
就没有目标版本——因为那个状态从未被记录。记了之后，回滚是「在当前状态上再走一步」，
历史始终是单调的，永远可逆。

## R-03 为什么回滚不还原名字

名字在所有者范围内唯一（005 的 `UNIQUE(owner_id, name)`）。回滚到旧版本时，
那个名字**很可能已经被另一个模板占用**（改名的常见动机就是「腾出这个名字给新的」）。
强行还原会撞 409，让「回滚」这个动作在最需要它的时候失败。

所以回滚只还原配置（含描述），名字保持现值。这个取舍写在 spec 与 UI 文案里
（「只还原配置」）。

## R-04 为什么导入重名是 409 而不是自动加后缀

自动加后缀（`xxx-2`）看似友好，实际制造了一堆**看不出区别的模板**：用户导入两次后
列表里出现 `日报助手` / `日报助手-2`，他无法判断哪个是新的、哪个可以删。

409 把「你已经有一份了」这个事实明确告诉用户，让他自己决定是删旧的还是改名。

## R-05 为什么导入要复校验

005 立过一条纪律（FR-022）：「模板不得成为绕过校验的旁路」——模板字段的约束必须与
Agent 逐字一致。导入是**外部输入**，如果直接 `AgentTemplate(name=..., tools=[...])`
建行，就绕过了工具白名单与数值范围。

所以 import 走 `AgentTemplateCreate`（带校验器的创建 schema），校验失败转 400 并带
前 300 字错误——不把 pydantic 的原始堆栈丢给用户。

## R-06 为什么可见与可改必须分开判

`get_template` 原本承担「能不能看」；023 让 team 模板对所有人可见后，
`update_template` 若继续复用它的判定，就会变成「能看到就能改」——测试直接抓到了这个
漏洞（队友 PATCH 返回 200）。

修法是显式两级：`get_template` 判**可见性**（owner / 内置 / team），
写操作各自再判 **owner**。这类「读权限被误用为写权限」的漏洞在有共享概念的系统里
反复出现，值得在代码里留一条注释。

## R-07 为什么不做公开市场

市场需要：审核（谁的内容能上）、举报、评分、下架、版权声明，以及最关键的
**内容责任**。内部工具的规模（几十到几百人）用「团队共享 + 搜索」就够，
上市场是给一个不存在的规模做工程。

真要做，正确形态是「公司内的模板库 + 部门归属」（020 的部门可以直接复用），
而不是一个独立的产品。

## R-08 为什么 `all` 要包含 team

两个选项：
- `all` = 内置 + 自己的（team 只在 `scope=team` 出现）；
- `all` = 内置 + 自己的 + team 的。

选后者：`all` 的语义是「我相关的全部」，用户不该为了看到同事共享的东西而切 tab。
这符合 007 立下的「只扩大不缩小」纪律——既有调用方看到的只会更多，不会更少。

代价是 005 的一条断言（`all` 里每一项都是内置或自己的）要同步放宽，我在测试里
注明了原因，而不是悄悄改掉。
