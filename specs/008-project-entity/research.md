# Research: 008 项目实体与需求归属

编号 `R-01…`。每条写**决策 / 依据（带实测或既有契约）/ 被否决的方案及理由**。
被否决的方案比决策本身更有价值。

## R-01：项目单人归属，不做成员表

- **决策**：`projects.owner_id` 单列归属，无 `project_members` 表。
- **依据**：① 路线图原文「P2 按实际组织形态按需添加」——组织形态（共享项目、
  部门、矩阵）被用户显式后置；② 实测当前 5 个用户各 2–6 条需求，没有一条
  需求被两人以上归因的先例；③ 007 刚建立的经手链已经解决了「一件活经过哪些人」
  的追溯，项目不需要重复回答这个问题。
- **被否决**：`project_members(project_id, user_id, role)` 多态归属。
  理由：它会把「谁能改项目名」变成权限矩阵问题（owner/admin/member 三态），
  而本轮连「项目归谁」都还没有真实使用数据支撑；先按单人跑一个阶段，
  用真实数据决定 P2 的成员模型，比现在拍一张权限表靠谱。

## R-02：删除项目 = SET NULL，不 RESTRICT 不 CASCADE

- **决策**：`requests.project_id` 外键 `ON DELETE SET NULL`；删项目不碰需求任何其他字段。
- **依据**：与 004 `requests.source_schedule_id` 的既有纪律一致——「规则删了，
  它建出的需求还在」。实测 007 通知表/经手表都挂在 request_id 上且
  `ON DELETE CASCADE` 只在**删需求**时触发，删项目不级联到它们。
- **被否决**：① `RESTRICT`（有需求的项目不许删）——用户只能先逐条改需求的
  归属才能删项目，20 条需求就是 20 次操作，删除动作实际不可用；
  ② `CASCADE`（删项目连带删需求）——需求上有 Run、经手链、通知、附件，
  连带删会一次性销毁大量不可再生成的数据，且与 004/006/007 全部纪律冲突。

## R-03：归档只拦「新建时可选」，不拦任何既有链路

- **决策**：`status=archived` 的项目：建/改需求的 `project_id` 校验拒绝（400），
  但详情、列表、`?project_id=` 筛选、分派、接收、退回、执行全部照常。
- **依据**：归档的用户意图是「这个项目做完了，别再往里面加东西」，
  而不是「这个项目里的进行中需求给我停下」。后者是停止业务，必须显式操作
  （取消 Run/退回需求），不能靠改一个项目字段顺带发生。
- **被否决**：归档即冻结其下需求（拒绝分派/执行）。理由：它让一个低风险的管理
  动作产生高后果的业务中断，且冻结的边界（进行中的怎么办？已接收的怎么办？）
  需要一整节状态机才能说清——范围失控。

## R-04：`project_name` 物化快照，不 JOIN

- **决策**：`requests.project_name` 可空字符串列；项目 PATCH 改名时同步
  `UPDATE requests SET project_name=:new WHERE project_id=:id`。
- **依据**：① 004 的 `source_schedule_name` 是同款模式，前端已有消费路径；
  ② 看板列表是「过滤 + count + 分页」三连，JOIN projects 会让 count 查询
  多一个 join 节点、让过滤条件多一张表的锁参与；
  ③ 改名是低频管理动作，一次批量 UPDATE 的成本可忽略。
- **被否决**：详情/列表实时 JOIN 取 name。理由：`GET /requests` 的
  `total` 计数与 `items` 分页必须同源，JOIN 后两处都要带 `projects`，
  分页深度越大扫描代价越高；且项目删除（SET NULL）后 name 必须一起清空，
  JOIN 方案要额外处理「project_id 有值但项目没了」的中间态（物化方案天然没有）。

## R-05：`project_id` 变更仅限需求创建者

- **决策**：`PATCH /requests/{id}` 中，其他字段维持 007 的
  owner-or-assignee 谓词；`project_id` 单独要求创建者，否则 403。
- **依据**：经手人把需求挪到自己名下的项目，创建者的「按项目看」视图会
  **静默**丢失这件活——没有通知、没有历史（经手链只记责任不记归属变更）。
  这与 007 反复强调的「可见性变更必须可解释」直接冲突。
- **被否决**：① 任何有编辑权的人都能改（与既有谓词一致、实现最省）——
  输在上面那条静默丢失；② 经手人可改但要发通知给创建者——通知能补救
  「知情」但补救不了「项目视图已经乱了」，且给经手链加第四种记录类型
  （归属变更）是把两个关注点搅在一起。

## R-06：未归属用 `?project=none` 表达

- **决策**：`GET /requests?project=none` 查 `project_id IS NULL` 的需求。
- **依据**：URL query 里传字符串 `"null"` 与「传了但值为空」无法区分，
  `?project_id=null` 会被前端序列化成四种样子（`null` / `"null"` / 缺省 /
  空串），是自找的歧义；`none` 是一个显式的、不可能与 UUID 冲突的哨兵值。
- **被否决**：`?project_id=` 缺省即不过滤 + 单独 `?unassigned=true`。
  理由：两个参数表达同一维度，组合语义（同时传 project_id 和 unassigned）
  需要额外定义；一个维度一个参数更硬。

## R-07：项目名唯一约束用普通 UNIQUE，不需要部分索引

- **决策**：`UNIQUE(owner_id, name)` 普通唯一约束 + 冲突时 409。
- **依据**：`owner_id` 非空（项目必有归属人），不存在 005 内置模板那种
  「owner_id 全为 NULL 导致唯一约束失效」的陷阱，因此不需要部分唯一索引。
  同名冲突在 service 层显式查一次后创建，并发下靠约束兜底
  （IntegrityError → 409，同 agents 同名处理）。
- **被否决**：全局唯一（不含 owner_id）——不同用户建同名项目太常见
  （「官网改版」这种名字），全局唯一会把第二个用户直接挡住。

## R-08：依赖边/DAG 明确不在本轮

- **决策**：不做 `request_dependencies` 表、不做拓扑排序、不做执行门禁。
- **依据**：用户 2026-11-18 路线图原文把「P2 按实际组织形态按需添加」放在
  「P1 项目容器」之后；且 007 spec §2.2 的留口把依赖与容器分成两件事。
  本轮先验证「容器」本身的价值（归类 + 筛选），依赖的语义（硬门禁/软提示/
  自动解锁/成环拒绝）在没有真实依赖数据前全是拍脑袋。
- **被否决**：顺手把依赖边一起做。理由：依赖会改 assign 热路径（007 刚定的
  RT<100ms 契约）与需求状态机（新增 blocked 态），两个新概念一次上线，
  出问题无法分辨是容器错了还是依赖错了。
