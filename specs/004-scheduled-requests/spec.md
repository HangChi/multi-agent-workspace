# Feature Specification: 定时调度（按规则自动建单并分配执行）

**Feature Branch**: `feat/004-scheduled-requests`
**Created**: 2026-11-17
**Status**: Draft
**Input**: User description: "004：定时调度。001-003 已完成，002 明确将「用户自定义定时任务」独立为特性 004。范围定为完整闭环（定时建单 + 自动分配执行 + 管理页）；错过的触发跳过并记录、不补跑；member 管理自己的调度且可指定 Agent 或组，admin 可查看全部。"

## 背景与动机

001 建立了「需求卡片 → 拖拽分配 → 编排执行 → 实时可见」的核心闭环，002 补齐了沙箱与工具边界，003 补齐了外部工具治理。但这套闭环的**触发方式始终是人手的**：用户必须自己想起来、打开看板、写一张卡片、拖到 Agent 上。凡是「每天出一份简报」「每周一汇总上周数据」这类重复性任务，用户只能靠记忆重复劳动。

本特性为工作台补上**时间维度的触发器**：用户定义一条调度规则（做什么 + 交给谁 + 什么时候），系统到点自动创建需求并按既有编排链路执行。执行的每一步仍然复用 001–003 已经建立的需求状态机、Run 编排、工具授权、成本熔断、审计和实时日志——调度只负责「按时按下分配按钮」，不得成为一条绕开这些边界的旁路。

**核心设计取舍（已与用户确认）**：

- **完整闭环**，而不是只建单。只建单不分配会退化成「自动生成待办列表」，用户仍要手工拖拽，价值大打折扣。
- **错过的触发跳过并记录，不补跑**。以 5 分钟一条的规则为例，服务停机 2 小时会积累 24 个待补触发；若全部补跑，恢复瞬间会向队列灌入 24 个请求，直接打爆并发限制与月配额。宁可丢失历史时点，也不制造雪崩。
- **member 管自己的调度，admin 可查看全部**，与既有资源归属模型一致；调度可指定单个 Agent 或一个 Agent 组。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建定时调度并看到下次触发时间 (Priority: P1)

成员为自己的重复性任务创建一条调度：填写要做什么（标题、描述、期望产出、优先级）、交给谁（某个 Agent 或某个组 + 编排策略）、什么时候（周期表达式）、是否启用。保存后立即看到这条规则的下次触发时间，并可随时启用、停用、修改、删除。

**Why this priority**: 这是特性的入口。没有可信的「下次什么时候跑」展示，用户不敢把有成本的自动化挂在上面。

**Independent Test**: 创建一条「工作日每天 9 点」的调度，验证返回的下次触发时间落在下一个工作日的 09:00（而不是当天已过的 09:00、也不是周末）；再创建一条非法表达式，验证被拒绝且给出可读原因。

**Acceptance Scenarios**:

1. **Given** 成员已有一个启用的 Agent，**When** 创建调度并填写标题、周期表达式「工作日每天 09:00」、目标为该 Agent，**Then** 系统保存规则并返回下次触发时间，该时间落在下一个工作日的 09:00。
2. **Given** 成员填写了无法解析的周期表达式，**When** 提交，**Then** 系统拒绝创建并返回可读原因，明确指向是哪个字段不合法，不创建任何规则。
3. **Given** 成员填写了「2 月 31 日」这类永远不会发生的表达式，**When** 提交，**Then** 系统拒绝并说明该表达式不会产生任何触发时刻。
4. **Given** 调度已创建，**When** 成员停用后再启用，**Then** 停用期间下次触发时间为空，启用后重新计算并展示，且不因停用时长产生补偿触发。
5. **Given** 成员把调度目标改为自己无权使用的 Agent，**When** 提交，**Then** 系统拒绝并说明原因为资源不存在或无权访问，不泄露他人资源的存在性。

### User Story 2 - 到点自动建单并分配执行 (Priority: P1)

调度到期时，系统自动按模板创建一张需求卡片，并按调度指定的目标与策略完成分配，走与手工拖拽完全相同的执行链路。用户在看板上看到这张卡片出现在「执行中」，在运行详情里看到完整的步骤日志，事后能分辨它是哪条调度产生的。

**Why this priority**: 这是特性对用户的全部价值所在。「自动建单但没人执行」等于没做。

**Independent Test**: 用一条每分钟触发的调度，验证一分钟内出现一张新需求卡片，其状态推进到执行中，产生了对应的 Run，且卡片上能追溯到来源调度；手工执行同一模板的结果与之在状态机与日志形态上无差异。

**Acceptance Scenarios**:

1. **Given** 调度已启用且目标 Agent 可用，**When** 到达计划时刻，**Then** 系统创建需求并完成分配，需求进入执行中状态，产生与手工分配一致的 Run 结构。
2. **Given** 调度目标是一个组且策略为并行分发，**When** 触发，**Then** 产生的 Run 结构与手工对同一组做同样分配完全一致（父 Run + 子 Run），不因来自调度而退化。
3. **Given** 一次触发已创建需求，**When** 用户在运行详情页查看，**Then** 能看到该运行来源于哪条调度、计划触发时刻与实际触发时刻。
4. **Given** 调度创建的需求已被执行，**When** 用户查看看板，**Then** 该卡片与手工创建的需求在同一套状态列中流转，不出现独立的「调度专属」状态。
5. **Given** 成员当月配额已用尽，**When** 调度触发，**Then** 分配被既有配额机制拒绝，系统记录该次触发失败及原因，需求不进入执行中，且不重复重试。

### User Story 3 - 错过的触发跳过并记录，不补跑 (Priority: P1)

调度器进程停机、或某次触发因前一次仍在执行而被跳过时，系统必须让用户看清「哪些时点没有跑、为什么没跑」，并且**不得**在恢复后成批补建需求。

**Why this priority**: 这是本特性最容易被做错、后果也最严重的地方。补跑逻辑写起来更"自然"，但一次长时间停机就会让恢复瞬间涌入几十个请求，打爆并发与配额，且用户根本无法分辨哪些是真实需要的。

**Independent Test**: 停掉调度器 2 小时（一条每 5 分钟的规则），恢复后验证：新增需求数为 0；系统产生一条覆盖该停机窗口的错过记录，标明错过的次数与起止时刻；下一次正常触发在恢复后的下一个计划时刻发生。

**Acceptance Scenarios**:

1. **Given** 一条每 5 分钟的调度，调度器停机 2 小时，**When** 恢复运行，**Then** 系统不补建任何需求，并产生**一条**覆盖该窗口的错过记录，包含错过的次数与实际起止时刻。
2. **Given** 前一次由该调度创建的需求仍在执行中，**When** 下一个计划时刻到达，**Then** 本次触发被跳过并记录原因（前次未结束），不并发叠加执行、不重复消耗成本。
3. **Given** 目标 Agent 已被归档，**When** 调度触发，**Then** 触发失败并记录可读原因，不创建需求。
4. **Given** 一条调度连续多次触发失败（目标失效等原因），**When** 达到失败阈值，**Then** 系统自动停用该调度并记录停用原因。
5. **Given** 错过记录已产生，**When** 用户查看该调度的触发历史，**Then** 能区分「已触发」「因错过跳过」「因前次未结束跳过」「失败」四种结果，并看到每次的时间与原因。

---

### User Story 4 - 触发历史与可追溯 (Priority: P2)

成员能查看一条调度的触发历史，并能从任一次触发反查它产生的需求与运行结果；管理员能查看全局调度列表用于排障（谁挂了、哪条一直失败）。

**Why this priority**: 自动化一旦出问题，用户的第一反应是「它到底跑没跑」。没有触发历史，用户只能靠翻看板猜。

**Independent Test**: 让一条调度成功触发若干次、跳过若干次、失败若干次，验证历史列表的四种结果计数正确，且每条成功记录能跳转到对应需求详情。

**Acceptance Scenarios**:

1. **Given** 一条调度已触发多次，**When** 成员打开它的触发历史，**Then** 能看到按时间倒序的记录，每条含计划时刻、实际时刻、结果、关联需求。
2. **Given** 一条触发记录关联了需求，**When** 用户点击，**Then** 跳转到该需求详情，且该需求详情能反向指出来源调度。
3. **Given** 管理员不是某条调度的创建者，**When** 管理员查看全局调度列表，**Then** 能看到该调度的名称、创建者、启用状态、下次触发与最近结果；但不能修改他人调度的内容。
4. **Given** 无关成员（非创建者、非管理员），**When** 访问某条调度或它的触发历史，**Then** 返回不存在或无权访问，不泄露调度内容。

---

### User Story 5 - 调度变更即时生效且不污染历史 (Priority: P2)

用户修改调度（改时间、改目标、改模板内容）或删除调度后，新规则只影响后续触发；已经由该调度产生的需求与运行必须保持原样，不因规则变更而被改写或消失。

**Why this priority**: 用户会反复调整周期。如果改一次规则就把历史运行改写成"新的目标 Agent"，排障与成本核算都会失真。

**Independent Test**: 让一条调度触发一次（产生需求 A），然后修改它的目标 Agent 与模板标题、再触发一次（产生需求 B），验证 A 仍指向原 Agent 与原标题，B 指向新配置。

**Acceptance Scenarios**:

1. **Given** 一条调度已产生需求 A，**When** 用户修改调度的目标与模板，**Then** 需求 A 及其运行保持原内容不变，后续触发使用新配置。
2. **Given** 一条调度正在被修改，**When** 修改保存时恰好到达计划时刻，**Then** 触发使用修改前或修改后的完整配置之一，不出现「目标已改但模板还是旧的」这种混合状态。
3. **Given** 用户删除一条调度，**When** 删除完成，**Then** 它不再触发，但历史触发记录与已产生的需求仍然存在并可追溯。
4. **Given** 一条调度已停用，**When** 到达原计划时刻，**Then** 不产生任何需求与触发记录（停用不是「跳过」，是「不存在这次触发」）。

---

### Edge Cases

- **周期表达式语义差异**：不同实现对「日期 + 星期」同时限定时是取并集还是交集并不一致。本特性 MUST 明确采用**交集**（两者都满足才触发），并在用户填写时给出可读说明，避免用户以为是"每月 1 号或每周一"。
- **表达式过于密集**：用户填写每分钟触发的规则时，系统必须受既有并发与配额边界约束，而不是无限建单。当触发频率高于系统能稳定承载的节奏时，应以「前次未结束则跳过」而不是排队堆积。
- **夏令时与固定时区**：周期表达式按一个显式时区求值。若该时区无夏令时（本项目默认时区即如此），行为全年一致；若将来支持有夏令时的时区，重复或跳过的那一个时刻必须被记录而不是静默丢弃。
- **系统时钟回拨或前跳**：下一次触发时间的计算必须能在时钟异常后自行收敛，不出现「永远等不到」或「连续狂跑」。
- **同一条规则被并发触发**：多个调度执行者或重复投递导致同一计划时刻被处理两次时，同一个计划时刻 MUST 只产生一张需求。
- **目标在触发瞬间被删除/归档**：触发失败并记录原因，不产生半成品需求（不能出现"需求建了但没分配"的孤儿卡片）。
- **模板内容引用了已不存在的资源**：触发时以完整配置为准，失败要可读，不得把内部标识符暴露给用户。
- **调度创建者被降级或删除**：其调度必须停止产生新需求，历史记录保留。
- **需求创建成功但分配失败**：不能留下「永远停在已创建」的卡片。要么整体成功，要么整体不发生并记录失败。
- **触发历史无限增长**：必须有不影响追溯主体信息的保留策略，避免单条调度积累出百万行历史。

## Requirements *(mandatory)*

### Functional Requirements

**规则定义与管理**

- **FR-001**: 系统 MUST 允许成员创建、编辑、停用、启用和删除属于自己的调度规则，每条规则包含名称、需求模板（标题、描述、期望产出、优先级）、执行目标（Agent 或 Agent 组 + 可选编排策略）和触发周期。
- **FR-002**: 系统 MUST 在保存规则时校验周期表达式，拒绝无法解析的表达式与永远不会产生触发时刻的表达式，并返回指向具体字段的可读原因。
- **FR-003**: 系统 MUST 在规则上展示下次触发时间，并在规则被修改、启用、停用后立即更新该时间。
- **FR-004**: 系统 MUST 对周期表达式采用明文约定的求值语义，其中「日期」与「星期」同时限定时 MUST 取交集（两者都满足才触发），并 MUST 在用户填写处展示该语义说明。
- **FR-005**: 调度 MUST 遵循既有资源归属与角色校验：成员只能管理自己的调度、只能把调度指向自己有权使用的 Agent 或组；管理员 MUST 能查看全部调度但 MUST NOT 修改他人的调度内容。
- **FR-006**: 系统 MUST NOT 因创建者无权访问某目标而透露该目标是否存在，拒绝理由 MUST 与「目标不存在」保持一致的措辞。
- **FR-007**: 系统 MUST 在停用状态下不产生任何触发与触发记录；重新启用 MUST 从启用时刻重新计算下次触发时间，MUST NOT 补偿停用期间的计划时刻。

**触发与执行**

- **FR-008**: 系统 MUST 在到达计划触发时刻时，按模板创建需求并完成分配，执行链路 MUST 与手工拖拽分配完全一致，MUST NOT 引入调度专属的状态或旁路。
- **FR-009**: 系统 MUST 保证「创建需求 + 完成分配」的原子性：任一环节失败时 MUST NOT 留下已创建但未分配的需求卡片。
- **FR-010**: 系统 MUST 让由调度产生的需求可追溯回来源调度，并记录计划触发时刻与实际触发时刻。
- **FR-011**: 系统 MUST 在触发前校验目标可用性（存在、未归档、有权限）与既有配额、成本、并发边界；校验失败时 MUST 记录失败原因并 MUST NOT 创建需求。
- **FR-012**: 同一个计划触发时刻 MUST 最多产生一张需求，即使触发被重复投递或存在多个调度执行者。
- **FR-013**: 前一次由该调度产生的需求尚未进入终态时，下一次计划时刻 MUST 被跳过并记录原因，MUST NOT 并发叠加执行。

**错过与失败处理**

- **FR-014**: 调度执行者停机或延迟后恢复时，系统 MUST NOT 补建停机期间错过的任何需求。
- **FR-015**: 系统 MUST 为每一段被错过的窗口产生**合并的**错过记录，包含错过次数与窗口起止时刻，MUST NOT 为每个错过的时刻各写一条记录造成记录爆炸。
- **FR-016**: 系统 MUST 区分并记录四种触发结果：已触发、因错过跳过、因前次未结束跳过、失败；每条记录 MUST 包含计划时刻、实际时刻与可读原因。
- **FR-017**: 一条调度连续触发失败达到配置阈值时，系统 MUST 自动停用该调度并记录停用原因与停用时所用的阈值。
- **FR-018**: 调度执行者 MUST 保证单条规则的异常不阻断其他规则的触发。

**历史与可追溯**

- **FR-019**: 系统 MUST 提供按调度查看的触发历史，支持按结果过滤，并能从成功记录跳转到对应需求详情。
- **FR-020**: 修改或删除调度 MUST NOT 改写已由该调度产生的需求与运行的内容；历史 MUST 保持其产生时的目标与模板。
- **FR-021**: 触发历史的保留 MUST 设置上限，超出后按时间淘汰最旧记录，同时 MUST 保留可用的汇总事实（最后触发时间、累计触发与失败次数）。

**安全与审计**

- **FR-022**: 调度规则的创建、修改、启用、停用、删除，以及每次触发的成功、跳过与失败，MUST 写入既有审计记录，至少包含操作者（或系统身份）、时间、调度、结果与关联需求。
- **FR-023**: 调度 MUST NOT 扩大其创建者原本拥有的权限：调度指向的目标与可调用的工具范围 MUST 在每次触发时按创建者当下的权限重新校验，MUST NOT 缓存已失效的授权。
- **FR-024**: 系统 MUST 限制同时被处理的调度数量，避免一次处理窗口内的任务堆积导致核心接口响应劣化；超出容量时 MUST 延后而不是丢弃，且延后 MUST NOT 演变成补跑。
- **FR-025**: 系统 MUST NOT 允许通过调度模板注入不属于该创建者的资源引用、附件或凭证。

### Scope Boundaries *(explicit exclusions)*

- **不含** 002 沙箱能力、003 外部工具治理的补做或重构；调度只消费它们已建立的边界（002/003 已完成，见各自 tasks.md）。
- **不含** 由调度直接触发「重跑一次历史运行」或「重试失败运行」；调度只创建新需求，重试属既有 Run 操作（001 已有 `POST /runs/{id}/retry`）。
- **不含** 一次性定时提醒或单次延迟任务；本特性只做周期性规则。
- **不含** 需求模板中的附件预置；创建需求时不支持携带附件，附件仍需用户手工补充（现有创建契约不支持附件，见 Assumptions）。
- **不含** 调度之间的依赖、串联与条件分支（如「A 成功后再跑 B」）；这属于工作流编排，超出定时器范畴。
- **不含** 分布式调度器的选主与高可用；v1 依赖单执行者 + 幂等约束（同计划时刻只建一张单）保证正确性。
- **不含** 秒级精度触发；最小粒度为分钟。
- **不含** 调度产生的成本独立核算；调度产生的运行计入创建者既有的月配额与目标 Agent 成本上限。

### Key Entities *(include if feature involves data)*

- **调度规则（Schedule）**: 一条周期性触发规则。含名称、所属创建者、周期表达式与其求值时区、下次触发时间、最近触发时间、启用状态、连续失败计数，以及触发目标的引用。
- **需求模板（ScheduleTemplate）**: 调度触发时要创建的需求内容，含标题、描述、期望产出、优先级。它是规则的一部分，不是独立实体。
- **执行目标（ScheduleTarget）**: 调度触发后把需求交给谁——Agent 或 Agent 组，以及可选编排策略；未指定策略时沿用既有默认（Agent 直接执行 / 组用组默认策略）。
- **触发记录（ScheduleTrigger）**: 一次触发处理的可审计事实。含所属调度、计划时刻、实际时刻、结果（已触发 / 错过跳过 / 前次未结束跳过 / 失败）、错过次数（合并记录时）、可读原因、关联需求与运行。
- **需求（Request）**: 既有实体，新增可选的「来源调度」关联用于追溯；不改变其既有状态机与字段语义。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 创建一条调度从填写到看到下次触发时间，在有现成 Agent 的前提下，95% 的操作可在 1 分钟内完成（基于既有分配受理 12ms 的实测基线，本操作无重活）。
- **SC-002**: 计划触发时刻与实际触发时刻的偏差，在不发生跳过与失败的正常情况下，95% 不超过 90 秒（执行者处理周期为 1 分钟，留一次处理的余量）。
- **SC-003**: 在「指向单 Agent」「指向组 + 并行分发」「指向组 + 顺序管道」三种配置下，由调度产生的 Run 结构与手工对同一目标做同样分配 **100% 一致**（父/子 Run 数量与关联、策略字段、授权快照存在性）。
- **SC-004**: 执行者停机 2 小时后恢复，由每 5 分钟规则产生的补偿需求数为 **0**；错过记录为 **1 条合并记录**且准确反映错过次数与窗口起止。
- **SC-005**: 同一计划时刻在重复投递与并发处理的测试下，产生的需求数为 **1**（不重复建单）。
- **SC-006**: 在 20 条调度同时到期的处理中，核心接口（看板列表、运行详情）的响应劣化不超过既有归因判据，且无请求失败；20 个触发全部到达确定结果（成功或带原因的跳过/失败），无静默丢失。
- **SC-007**: 调度规则与触发事件的审计覆盖率 **100%**，抽查记录中不含凭证原文、请求头密钥或不属于该创建者的资源内容。
- **SC-008**: 在包含「停用中」「目标已归档」「创建者被降级」「前次未结束」四种情形的验证中，未按预期发生执行的次数为 **0**，且每种情形都有可读原因。
- **SC-009**: 修改调度目标与模板后，已产生需求的目标与标题被改写的条数为 **0**。

## Assumptions

- **周期表达式语义**：实测本项目的任务框架（Celery 5.7.0）在「日期」与「星期」同时限定时取**交集**（`0 9 1 * 1` 实测只在「既为 1 号又是周一」的日子触发，标准 cron 则取并集）。规格采用交集并明示用户；这比自行实现一套 cron 解析器更不易出错，代价是与部分用户对 cron 的直觉不同。
- **时区**：表达式按一个显式时区求值，默认 `Asia/Shanghai`（与既有任务框架配置一致）。该时区无夏令时，因此「重复/跳过的时刻」在 v1 不会出现，但设计上仍保留该情形的位置。
- **最小粒度一分钟**：调度处理周期为 1 分钟，因此 SC-002 的偏差上界取 90 秒。
- **需求创建不支持附件、无截止时间**：实测现有创建契约（`RequestCreate`）只接受标题、描述、期望产出、优先级；`requests` 表实际也没有 `deadline` 列（`docs/architecture.md` 数据模型中列的 deadline 未落地）。因此需求模板只含这四项。
- **单执行者**：v1 只部署一个调度执行者，正确性靠「同计划时刻幂等」约束保证，而不是靠分布式选主。
- **错过的判定**：仅当计划时刻已过且超过一个处理周期仍未处理时，才计为错过；恰好在一个周期内的延迟按正常触发处理（不记错过）。
- **「前次未结束则跳过」的判定对象**：判定的是**该调度最近一次触发产生的需求**是否处于非终态，而不是全局任何需求。这样用户对同一目标手工创建的卡片不会阻塞调度。
- **失败自动停用阈值**：沿用项目既有的连续失败阈值风格（002 工具拒绝阈值为 5 次），默认 5，可配置。
- **触发历史保留**：默认保留最近 500 条/调度或 90 天（后者沿用沙箱数据保留期），并以汇总字段保底。具体数值在实现阶段以实测数据量校验。
- **调度计入成本**：调度产生的运行完全继承创建者的月配额与目标 Agent 的成本上限，不存在「定时任务免配额」的特例。
