# Research：依赖图谱与自动启动（021）

## R-01 为什么关键路径按「跳数」而不是工期

关键路径的经典定义依赖**每个任务的时长**。系统里没有任何工期数据：
需求没有「预计工时」，历史 Run 的耗时受 LLM 与沙箱影响波动极大，用它当权重
会把「昨天刚好快」的活排到前面。

跳数（边权 1）至少表达一件事：**这条链串了几道工序**。链越长，串行风险越大
（任何一环卡住，后面全等）。这是在没有工期数据时唯一诚实的近似，代码里也写清
「有工期数据后再换权重」。

## R-02 为什么只返回下游子图，不做全图

全图（所有需求 + 所有边）在项目变大后会变成几百上千节点：一次往返的数据量、
前端渲染、以及**没有意义**——没人需要一次看全公司的依赖。

下游子图回答的是用户点开某条需求时真正的问题：「这条活后面还挂着谁」。
上游（我依赖谁）已经在详情的前置列表里了（009 的区块），不需要重复。

## R-03 为什么有环时不算关键路径

最长路径在环上无定义（可以绕圈无限长）。009 的加边已经拒绝成环，所以正常数据
不会有环；但图谱是**读**路径，防御性地处理：`has_cycle=true`，`critical_path=[]`，
拓扑序返回已排序部分。前端据此显示「检测到环」而不是画一条假路径。

## R-04 自动启动为什么是 Celery 任务，而不是在 settle 里直接分配

settle 是「终态收敛」的唯一汇聚点（009 起所有终态都经它）。如果在里面直接
建 Run：

1. **事务变长**：settle 已经在锁需求行，再叠加分配（锁更多行、查配额、建 Run）
   会扩大锁持有时间；
2. **入队时机**：分配后必须 commit 才能把 Run 入队（否则 worker 读到不存在的
   Run），而在 settle 的事务里 commit 会破坏「终态 + 通知 + 审计」的原子性；
3. **失败隔离**：自动启动失败（配额超限、agent 被删）不该让 settle 失败。

交给任务：settle 只 `delay()` 一条消息，任务独立事务、可重试、失败只记日志。

## R-05 任务的幂等三校验

任务可能在以下情况被重复/过时地触发：
- settle 重试、消息重复投递；
- 用户在解锁后又加了新前置；
- 用户中途关掉了 `auto_start` 或删了 agent。

所以任务开头重查三件事：**配置还在**、**前置仍全终态**、**assign 自己的门禁**。
任何一条不满足就安静退出——自动启动是「锦上添花」，它失败绝不该产生一个
「奇怪状态的 Run」。

## R-06 为什么自动启动的权限是「创建者或项目 owner」

配额记在 `request.owner_id`（007 起的纪律）。让「经手人」打开自动启动，等于
让别人替你花钱。所以权限与「改项目归属」同档：归属级决策由归属人做。

## R-07 为什么前端不做图形（DAG 可视化）

一张真的 DAG 图需要布局算法（dagre/elk）、缩放平移、节点点击命中，而且在小屏
上几乎不可用。而 95% 的使用场景是「看这条链有哪几道工序、哪个是瓶颈」——
**一个按拓扑序的列表 + 关键路径徽章**就够，还能用键盘和读屏。

真到需要「看一张大图」的时候（几十个节点、跨项目），再引入图形库，那时它的
交互模型也才想得清楚。

## R-08 节点上限 300 的由来

一次图谱往返的数据量（每节点约 200 字节）在 300 节点时约 60KB，前端渲染一次
列表可接受；再大就该分页或按项目过滤。超限时返回 `truncated=true` 而不是
静默截断——静默截断会让人以为「后面没活了」，这是最危险的误导。
