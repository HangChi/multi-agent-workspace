# 并发压测记录（2026-11-17）

工具：`deploy/verify/load_test.py`（异步 httpx，预热 10 次，连接池=并发数）

环境：Docker Desktop（Linux VM，**2 vCPU** 分配给 api 容器，`--workers 2`），
前端 nginx → api，PostgreSQL/Redis/MinIO 同机。这是开发机，不是生产规格。

## 结果

| 目标 | 并发 | 请求数 | 吞吐 | p50 | p95 | p99 | max | 错误 |
|---|---|---|---|---|---|---|---|---|
| `/api/v1/health`（不碰 DB） | 100 | 3000 | **818 req/s** | 88 ms | 336 ms | 524 ms | 905 ms | **0** |
| `/api/v1/health` | 200 | 4000 | 752 req/s | 192 ms | 730 ms | 1160 ms | 2145 ms | **0** |
| `/api/v1/health/ready`（DB+Redis） | 50 | 1500 | 383 req/s | 93 ms | 380 ms | 563 ms | 776 ms | **0** |
| `/api/v1/health/ready` | 100 | 2000 | 304 req/s | 130 ms | 1426 ms | 2478 ms | 4572 ms | **0** |

## 怎么读这些数字

1. **没有任何错误**：两条路径在 200 并发下都是 0 失败。说明连接池、uvicorn
   并发、nginx 反代在 100~200 并发这个量级都不会打出 5xx。
2. **吞吐在 ~800 req/s 封顶**：并发从 100 加到 200，吞吐反而从 818 降到 752，
   延迟翻倍 —— 典型的 CPU 饱和（2 vCPU）。此时加并发只会加排队，不会加吞吐。
3. **就绪探针比存活探针慢 2.5 倍**：每请求多一次 DB `SELECT 1` + 一次 Redis ping。
   100 并发下 p95 冲到 1.4 s，说明瓶颈在「每请求一次数据库往返」而不是应用逻辑。
   生产上这不是问题（探针每 10s 一次），但**不要把它当业务接口的容量指标**。
4. p99/max 的长尾（2.4 s / 4.5 s）来自排队：`pool_size=10 + overflow=20` 每个
   worker 最多 30 条连接，100 并发时超出的请求在池上等待。

## 结论与建议

- 「上百并发」在本机验证为**可用**（0 错误、吞吐线性到 CPU 上限），但**延迟不达标**
  （默认守护阈值 p95 ≤ 500 ms 在 100 并发下被突破）。两个数字要分开看：
  能扛住 ≠ 快。
- 需要更高吞吐时，优先加 **CPU/worker 数**，而不是调大连接池 —— 连接池只是把
  排队从池外挪到池内。
- 真实业务接口（带 JWT 校验 + 列表查询）会比探针慢，容量评估要用
  `--url /api/v1/requests --token <jwt>` 复测；本次没有生产 token，未测。

## 复现

```bash
python deploy/verify/load_test.py \
  --url http://127.0.0.1:8080/api/v1/health/ready \
  --concurrency 100 --requests 2000
```

脚本在错误率 >1% 或 p95 >500ms 时非零退出。这两个默认值只是「明显不可用」的
兜底，生产阈值应按机型与业务 SLA 重设（见 `--max-error-rate` / `--max-p95-ms`）。
