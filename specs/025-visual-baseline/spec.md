# Feature Specification: 视觉回归基线（025，对应 015 的 T024）

**Status**: Implemented（2026-11-21）

## 问题陈述

015 的 UI 整改完成后，**没有任何机制阻止下一次样式改动把布局弄坏**。现有测试
（vitest + e2e）断言的是「元素存在/可点/文案对」，不是「看起来还是那个样子」：
把按钮从右侧挪到左、把卡片圆角改成直角、把侧栏宽度改 40px，所有测试都会绿。

T024 一直挂着，此前的理由写的是「无 e2e 基建」；011 之后基建有了，剩下的问题是
**怎么做才不变成一堆 flaky 的红**。

## 设计

### 只做三个页面

| 页面 | 为什么稳定 |
|---|---|
| `/login` | 无数据、无时间戳、无计数 |
| 新账号的看板空态 | 空态文案固定，无卡片 |
| 新账号的模板页空态 | 验证设置壳（左导航 + 内容区）没走样 |

**不做**看板/项目/需求的内容态：它们的数据由用例随机造（标题带 run_id），
截图每跑都不同，做像素基线只会产出假红——假红比没有基线更糟，因为它训练人忽略红。

### 比对实现

原生 `sync_playwright` 没有 `to_have_screenshot`（那是 pytest-playwright 插件的
语义），所以用 Pillow 自己比：

- 尺寸不同 → 直接失败（布局结构性变化）；
- 单像素某通道差 ≤12 视为抗锯齿噪声；
- 变化像素占比 ≤2% 通过；超出则报错并提示「确认是预期变更就删 PNG 重生成」。

### 首次运行 skip，不是 pass

基线缺失时生成并 **skip**，消息写明「基线不存在，已生成 X」。
用 pass 会让人以为比对过了；用 skip 让「这条基线是我刚造的」显式可见。

## 成功标准

- SC-001 三个页面首次运行生成基线并 skip（3 skipped）。
- SC-002 第二次运行真实比对，3 passed。
- SC-003 把某个页面的 CSS 改坏（如侧栏宽度）后，对应用例失败并给出差异比例。

## 实测（2026-11-21）

- 新增 `e2e/tests/test_visual.py`（3 例）+ `e2e/tests/screenshots/*.png`（3 张，约 900KB）；
- 第一次跑：3 skipped（生成基线）；第二次跑：**3 passed**（真实比对，稳定）。

## 范围外

- 全站截图（几十页 × 多状态，维护成本远超收益）；
- 元件级 Storybook 视觉测试（项目没有 Storybook，且组件测试是 jsdom 的，
  引入真实渲染的组件基线是另一个基建）；
- 跨浏览器（只跑 Chromium：WebKit/Firefox 的字体渲染差异会让基线失去意义）。
