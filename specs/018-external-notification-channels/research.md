# Research：外部通知通道（018）

## R-01 为什么先做 Webhook、邮件留独立特性

见 spec 的问题陈述表。补充一条工程理由：**邮件的失败是静默的**（进垃圾箱、被退信策略
丢弃），我们甚至无法可靠判断「用户到底收到没有」；而 Webhook 的成功/失败是一个
HTTP 状态码，投递记录能如实反映。先做能被验证的那条通道。

## R-02 SSRF：为什么必须复用 002 的判定，以及残余风险

**更简单的做法**：保存时用 `urlparse` 判一下 host 不是 `localhost`。

**为什么不行**：`localhost` 只是一万个内网写法里的一种。`127.0.0.1`、`0.0.0.0`、
`[::1]`、`10.x`、`192.168.x`、`169.254.169.254`（云元数据，能取临时凭证）、
以及「外网域名解析到 127.0.0.1」——字符串判断一个都挡不住。

**做法**：抽 `app/core/net_guard.py`，把 002 `read_url.py` 里的
`_BLOCKED_NETS` / `_is_blocked_ip` / `resolve_public_hosts` 移过去，两处共用。
校验在**保存时**做（用户立刻得到 400），**投递时再做一次**（DNS 可能已变）。

**残余风险（如实记录）**：投递时我们无法像 `read_url` 那样「校验与连接用同一份解析
结果」——Celery 任务里用的 httpx 会在连接时自行解析。理论上存在 DNS rebinding 窗口。
缓解：
1. 不跟随重定向（`follow_redirects=False`）——302 到内网这条路直接堵死；
2. 投递前再校验一次，缩短窗口；
3. 目标主机是**同一租户自己的配置**（不是 LLM 可控输入），攻击者要先能改配置，
   而改配置需要登录。威胁模型与 `read_url`（LLM 可控）不同，风险等级更低。

如果后续把 webhook URL 开放给「非可信输入」（例如从模板导入），必须升级为
「解析后直连 IP + Host 头」的强制模式。

## R-03 为什么每条通知一条投递，不做聚合

聚合（每 5 分钟把 N 条合并成一封）能省请求，但它把「实时性」这个核心价值削掉一半，
并且引入「窗口怎么定、迟到的事件怎么办、聚合记录和通知怎么对账」三个新问题。
内部工具的通知量级是「每人每天几条到几十条」，先按原样投递；真到了噪声问题，
再在**事件类型订阅**层面解决（这个已经做了），而不是在投递层合并。

## R-04 at-least-once 而不是 exactly-once

超时后无法确定对方是否已处理：不重试 → 可能丢；重试 → 可能重复。
分布式投递里「恰好一次」需要接收端参与（幂等键 + 去重表），这不该由我们单方面承诺。

**结论**：at-least-once，头部带 `X-AW-Delivery`（投递 id）让接收端自己做幂等。
这条写进 contracts，避免使用者以为「重试等于重复是 bug」。

## R-05 为什么 4xx 不重试、429 要重试

- `5xx` / 超时 / 连接失败：对方暂时性问题，重试有意义；
- `4xx`（400/401/403/404）：URL 错了、secret 不匹配、接口路径变了——重试三次
  只是把同一个错误重复三遍，还拖慢队列。**不重试，直接把错误记在投递记录里**；
- `429`：对方明确说「慢点」，重试是对的（我们的退避正好是它要的）。

## R-06 为什么暂不做投递频率限制

风险是「一个用户配 50 个通道 + 高频事件」把 worker 打满。三条理由先不做：
1. 通道数天然受限（每人手工配，一般 1~3 条）；
2. 事件本身有上游节制（分派/完成都是人触发的低频事件）；
3. 真出问题，`aw_celery_queue_depth` 告警会先响（Phase 3 已有）。

先把「看到的投递记录」做出来，有了数据再定阈值，而不是拍一个数字。

## R-07 签名为什么是 `timestamp.HMAC(body)` 而不是「一个固定 header 带 secret」

固定 secret header 有两个问题：**明文传密钥**（中间层日志能看到）和**可重放**
（抓到一次请求就能无限重放）。

`X-AW-Timestamp` + `HMAC(secret, f"{ts}.{body}")` 让接收端能：① 验来源（没有 secret
算不出）；② 验新鲜度（拒绝超过 5 分钟的 ts）；③ 验完整性（body 被改则签名不匹配）。

选 `sha256=` 前缀（GitHub/Stripe 同款），接收端实现时不会搞错算法。

## R-08 secret 为什么明文存库

HMAC 需要原始 secret，加密存储就要在投递时解密（密钥管理另起一套）。
本项目 secret 由服务端生成（32 字节 urlsafe），只在需要时读出来算 HMAC，
**不回显给前端、不写日志**。DB 已经是最高敏感级别的存储（含 JWT secret 配置），
在它之上再加一层加密带来的收益小于运维复杂度。

边界：`GET` 列表只返回 `secret_configured: true`；重置是「生成新的」，不提供查看。

## R-09 为什么单独一张投递记录表，而不是在通知 payload 里写状态

通知是「发生了什么」的不可变事实（007/017 的纪律），投递是「我们尝试送达的过程」，
两者的生命周期和写入方都不同（通知写一次，投递状态会更新多次）。
混在一张表里会让每次重试都去 UPDATE 一条历史事实。

投递记录也是 US3 的载体：没有它，「配好了没收到」无法排查。
