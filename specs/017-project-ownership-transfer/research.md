# Research：项目所有权移交（017）

记录每个决策「为什么更简单的做法不行」。评审时先看这份。

---

## R-01 为什么是独立端点 `POST /projects/{id}/transfer`，而不是 `PATCH owner_id`

**更简单的做法**：`ProjectUpdate` 加一个 `owner_id` 字段，复用现有 PATCH。

**为什么不行**：

1. **它不是一个字段更新。** 移交要同时改归属、增删成员行、发通知、写独立审计——把它塞进
   PATCH 会让 `update_project` 从「改名同步快照」变成半个权限迁移器，两类语义混在一个
   入口里，之后每次动 PATCH 都要考虑「会不会碰到 owner 逻辑」。
2. **错误码语义不同。** PATCH 的 409 只来自同名；移交的 409 有四种（自移交、非成员、
   viewer、同名）。混在一起后，前端拿到 409 无法分辨该提示什么。
3. **016 的错误码矩阵按端点声明。** 独立端点才能写清「谁能调、失败怎么回」，
   把 owner 变更藏进 PATCH 会让矩阵出现一个隐形的特权字段。

同 006 的「重试」也走独立端点（`POST /runs/{id}/retry`）而不是「PATCH status=queued」，
理由形状一致。

## R-02 为什么目标必须是**现有成员**，而不是任意用户

**更简单的做法**：不校验成员关系，直接按 `new_owner_id` 移交——反正 owner 也是人。

**为什么不行**：

1. **移交是接力，不是空降。** 接手人突然拥有一个项目（含全部需求、成员、历史），
   而他从未参与过这个项目——这既不安全也不符合直觉。要求「先加为成员」等于让 owner
   显式承认「这个人要进这个项目」，多一步但语义正确。
2. **它顺手构成一条滥用通道。** 不校验成员关系，任何 owner 都能往任意用户的
   「我的项目」里塞东西（且是持续可见的），这类「被动接收」在协作工具里通常要
   对方同意。要求先加成员无法完全解决（加成员本身不需要对方同意），但至少把动作
   拆成两步、留下两条审计记录，事后可追溯。
3. **实现成本几乎为零**：本特性已经要查用户角色，多一条成员查询不影响复杂度。

## R-03 目标用户不存在为什么回 404，而不并入 409

**背景**：016 立下的纪律是「非相关人访问资源一律 404，且 message 与不存在逐字相同」，
目的是防**资源 id 枚举**。

**这里的差别**：用户 id 的**存在性本来就不是秘密**——`GET /users/options` 对全体成员
返回可指派用户列表（007 为分派面板加的）。也就是说，任何人已经能列出所有用户 id。
对一份已经公开的名单再「用 404 掩盖存在性」是无意义的，反而让「id 打错了」变成一个
无法诊断的 409。

**更关键：这已经是既有先例。** 010 的 `add_member` 就是先 `db.get(User, id)`，
不存在回 404「用户不存在」、停用回 400「用户已停用」。017 只是延续同一条边界，
不是新开口子。

因此：`new_owner_id` 不存在 → **404「用户不存在」**；已停用 → **400**；
存在且在职但不是成员 → **409**。这条边界写进 contracts，避免以后有人按
「016 一律 404」把它改错。

## R-04 `keep_as_member` 默认 true，且**显式**传参

**考虑过的三种做法**：

| 做法 | 问题 |
|---|---|
| 固定「原 owner 变成成员」 | 离职场景会留下「已离职但仍挂名」的成员行，且原 owner 仍能读写项目——这是**权限残留**，安全上最差的一种默认 |
| 固定「原 owner 完全退出」 | 转岗/交接场景里原经手人失去历史访问，要请新 owner 再把他加回来，来回两次 |
| 一个布尔参数，默认 true | 默认值仍有权限残留风险，但**保留访问是更常见的工作流**（交接不等于立刻断联） |

**结论**：参数化，默认 `true`（保留访问），离职场景显式传 `false`。
默认值在 UI 上用文案说明白：「移交后你仍是成员，可继续查看；取消勾选则完全退出」。
风险由**显式文案 + 审计 detail 记录该值**承担，而不是靠一个静默的默认值。

## R-05 校验顺序为什么是：归属 → 目标存在 → 目标角色 → 目标成员 → 同名

顺序不是随意的，每一条都是为了避免泄露或误判：

1. **归属（404/403）先判**：陌生人调这个端点必须拿 404，且**不能**因为「他传的
   new_owner_id 不存在」而先回 404「用户不存在」——那会让陌生人用这个端点探测
   项目是否存在（故意传一个不存在的用户，若回「用户不存在」说明项目那关过了）。
   这是 016 枚举防护的直接推论。
2. **目标存在性**：到这一步调用者已经是 owner（确定相关人），才允许区分用户不存在。
3. **目标角色**：viewer 不能接项目——viewer 在 010 的模型里连项目入口都没有
   （`nav.ts` memberOnly），让他当 owner 会造出一个「有项目但进不去」的怪状态。
4. **目标成员关系**：R-02。
5. **同名冲突**：放最后，因为它是唯一需要读「目标用户名下项目」的检查，
   而且它失败时**没有任何副作用**，放在锁内做刚好。

## R-06 同名冲突为什么必须显式查，不能靠 `uq_projects_owner_name` 兜底

**更简单的做法**：直接 UPDATE `owner_id`，让数据库抛唯一约束异常，全局异常处理器
转 409。

**为什么不行**：现有全局处理把 `IntegrityError` 转成 409 时**不带约束语义**，
前端只能显示「数据冲突」。而这里的冲突是最需要解释的一类：用户刚点了「移交给老张」，
需要知道「老张已经有一个叫『官网改版』的项目，请先改名或换人」。
显式查询（`SELECT 1 FROM projects WHERE owner_id=? AND name=?`）在锁内执行，
能给出可读 message；唯一约束仍然保留作为最后一道并发防线（两个请求同时移交到同一人
且都通过查询——概率极低，但那时 409 兜底也不算错）。

## R-07 为什么只通知新 owner，不给其他成员发

**考虑过**：给所有成员发「项目创建者已从 A 换成 B」。

**为什么不做**：

1. 010 的成员事件（加入/移出）必须通知，因为**访问权变了**。而 owner 变更对普通成员
   的访问权没有任何影响——他们照旧读写项目内需求。
2. 一个项目可能有几十个成员，一次交接就是几十条通知，而其中没有一条需要成员采取行动。
   通知的价值上限决定它不该广播。
3. 成员在项目页能看到 owner 徽章变化，这是**被动可见**的信息，不需要推送。

若后续真的需要（例如 owner 变更需要成员确认），那属于审批流，是独立特性。

## R-08 为什么没有数据库迁移

`projects.owner_id` 与 `project_members` 都是既有结构，本特性只改值。**不加**
`transferred_at`、不加 `transfer_history` 表：

- 「上次什么时候换的手」在审计表里有（`project_transfer` + detail），加冗余列要维护一致性；
- 移交历史属于「谁动过什么」的审计范畴，不是项目实体的属性。

**回滚面**：本特性无 schema 变更，回滚 = 回退代码，不需要 downgrade 迁移。
但要注意**数据回滚不可自动**——已移交的项目不会因为回滚代码而自动退回，
这点写进 quickstart 的回滚说明。

## R-09 并发：为什么锁项目行，而不是锁两次

移交要读「目标用户名下项目」并写「项目的 owner_id」，两者之间存在竞态：
两个不同的项目同时移交给同一个人、且新 owner 名下有同名项目时，两个请求可能都通过
同名检查。

**做法**：`SELECT projects ... FOR UPDATE` 锁的是**被移交的项目行**，
保证同一项目的移交/改名/删除/踢人串行；同名竞态（不同项目指向同一人）由
`uq_projects_owner_name` 兜底转 409。不额外锁用户行——锁用户会把「同一个人接收
多个项目」变成串行，收益为零（唯一约束已经保证正确性）。
