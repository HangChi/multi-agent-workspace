## Gate definition change for the strict P95 check (2026-11-16)

The core API P95 gate has been failing on every native run, and three instrumented
runs (`43883817877`, `43886357347`, `43889023691`) show why: the same sampler also
hits `GET /api/v1/health`, a database-free endpoint, from the same client, pool and
uvicorn processes. That control degrades by 1.93x, 1.93x and 6.0x in the load
window, while the measured endpoints degrade by 2.40-9.04x. On a 4-vCPU runner that
simultaneously hosts 2 uvicorn workers, 8 Celery processes, PostgreSQL, Redis, MinIO
and the harness, every process loses CPU to the load, so the absolute ratio mostly
reports the host's contention; the same measurement on a 10-core Docker Desktop
machine yields 0.99.

The verdict now divides the endpoint's ratio by the control's ratio, so only the
degradation an interface suffers *beyond* an equally starved endpoint that does no
work counts. Nothing else moved: no warm-up, no excluded sample, no retry, no
clipped outlier, same endpoints, and the absolute ratio plus both distributions are
still published in `metrics.core_api_p95`.

The attributed limit was raised from 1.2 to 1.75 on 2026-11-17 by the project
owner, after seven native runs produced attributed ratios between 0.91 and 1.56
(0.91, 0.97, 1.03, 1.09, 1.21, 1.23, 1.24, 1.27, 1.37, 1.39, 1.45, 1.49, 1.56).
1.75 leaves roughly 12% headroom above the observed maximum; a doubled
endpoint-specific degradation (2.0) is still rejected, so the gate keeps
catching a regression of the interface rather than of the host. A deployment that slows
its own reads still fails - `test_a_control_cannot_absorb_a_real_endpoint_regression`
pins a control at 2.0x against an endpoint at 3.0x and requires the gate to fail -
and a missing control series or a failed control request fails closed. This does not
complete the gate: the next native run has to show attributed ratios within 1.2.

## Verified follow-up changes

- **The first native CI run of the 003 acceptance failed at Worker readiness and exposed a harness portability defect, now fixed and awaiting native confirmation.** Run [43840065099](https://github.com/HangChi/multi-agent-workspace/actions/runs/43840065099) (`7373f41`) reached `deployment_ready` and stopped there with `own Celery worker did not become ready` and nothing else in the published artifact. Root cause, reproduced on this host by serving the same material through a Docker volume — where the kernel really enforces uid and mode, unlike a Docker Desktop bind mount: `generate_tls()` used `tempfile.mkdtemp()`, which leaves the directory 0700 and owned by whoever ran the acceptance, while the Worker container runs as uid 10001. On a native Linux daemon the bind mount therefore hid the CA bundle from the Worker, `SSL_CERT_FILE` made `ssl.create_default_context` raise while the application was being imported (litellm builds its httpx client at import time), and the Worker exited with status 2 before it could answer `inspect ping`. The fix makes the directory traversable and the trust bundle and certificate readable (0755 / 0644) while keeping the fixture's private key at 0600, and `wait_worker` now records bounded, credential-free evidence — container state, last worker log lines, the ping reply — in the artifact instead of a single sentence; reverse controls pin both the mode bits and the redaction. Every earlier local run passed because Docker Desktop serves bind mounts permissively, so the local evidence was never a native-Linux proof: the fix is confirmed by the volume reproduction, and a native CI rerun is still required before the native gate may be claimed.

- **Real-stack deployment acceptance found four product defects (`4abebb8`), each with a regression test verified to fail without its fix.** (1) The server-detail endpoint did not eager-load `ExternalToolVersion.listings`, so any server with a listing returned 500. (2) Nothing advanced `ExternalToolServer.status` to `published`, so no external tool could ever be granted or called; a refresh now runs on the transitions that can publish a server. (3) An invocation row was written before the Step row it references, raising a foreign-key violation; the runner now creates the Step before the executor runs and `_persist_steps` fills in a pre-created running step instead of inserting a duplicate — the same ordering the sandbox path already used. (4) `MCPClient._request` caught `httpx.TimeoutException` and re-raised it as `MCPTransportError`, so the documented `timeout` category was unreachable and the same overrun was classified by a race between the caller's deadline and the transport's own timeout; deadlines now reach the caller unchanged. None of these was reachable by the in-session suites: the first two need a real HTTP deployment, the third needs a real database with the constraint enforced, and the fourth needs a real deadline against a real slow server.
- **The acceptance also caught two defects in its own measurement (`4abebb8`), both now pinned by reverse controls.** The fixture's concurrency peak counted every concurrent HTTP request — including each session's `initialize` handshake — so it measured a stricter quantity than the per-server lease promises; it now counts only overlapping `tools/call`. Then it counted a handler still sleeping after its client had abandoned it, so ten deliberately-slow calls that outlive the Worker's 10 s deadline looked like ten concurrent ones and the lease bound could never be observed from outside; a call is now counted only while a client is still waiting for it, which is what FR-017's "release the call's resources at the bound" means. The deadline is wired from one value (harness constant → compose env → fixture flag) and a control test resolves the compose file to assert all three agree with the Worker's `MCP_CALL_TIMEOUT_SECONDS`. Separately, the fail-closed check polled a member's run as the governance account and hit the API's deliberate 404-for-non-owners behaviour; `wait_run` now takes the owning identity.
